## 1. What is Cloud Build? ⭐⭐⭐⭐⭐

### 🔹 Definition

**Google Cloud Build** is a fully managed, serverless Continuous Integration and Continuous Delivery (CI/CD) platform. It imports source code, executes build and test instructions within isolated containerized environments, and produces deployable artifacts (such as container images, binaries, or deployed infrastructure).

```
[ Source Code ] ──► [ Cloud Build Engine ] ──► [ Test & Package ] ──► [ Artifact Registry / Deploy ]

```

---

### 🔹 What Problem Cloud Build Solves & CI/CD Fundamentals

* 🔄 **Continuous Integration (CI):** Automates code linting, unit testing, and artifact compilation on every commit, catching bugs before integration.
* 🚀 **Continuous Delivery/Deployment (CD):** Automates releasing tested artifacts to staging and production environments (e.g., Cloud Run, GKE).
* 🛠️ **Zero Server Maintenance:** Traditional build servers require OS patching, scaling worker fleets, and managing build agent disks. Cloud Build manages all underlying build infrastructure automatically.

---

### 🔹 Cloud Build vs. Jenkins vs. GitHub Actions

| Feature / Metric | ☁️ Cloud Build | 🏗️ Jenkins | 🐙 GitHub Actions |
| --- | --- | --- | --- |
| **Infrastructure** | Fully Serverless (Google-managed) | Self-hosted VMs / Master-Worker nodes | Hosted runners or Self-hosted |
| **GCP Integration** | Native IAM, Secret Manager, VPC integration | Requires plugins and service account keys | Uses Workload Identity Federation |
| **Execution Model** | Container-native (every step is a container) | Host process or Docker plugin | VM runner or Container action |
| **Maintenance** | Zero operational overhead | High (plugin updates, VM scaling, disk cleanup) | Low to none |
| **Best For** | Native GCP deployments & container workflows | Complex legacy enterprise pipelines | Repositories hosted directly on GitHub |

---

### 🔹 When to Use Cloud Build

* Building container images directly within Google Cloud without managing local Docker daemons.
* Deploying natively to Google Cloud targets (**Cloud Run**, **GKE**, **App Engine**, **Compute Engine**).
* Requiring private network access into Google Virtual Private Clouds (VPC) via Private Pools.

## 2. Cloud Build Architecture ⭐⭐⭐⭐⭐

```
┌─────────────────────────────────────────────────────────────────────────────────────────┐
│                                 CLOUD BUILD ARCHITECTURE                                │
├───────────────────┬───────────────────────────────────────────────┬─────────────────────┤
│ 1. Event Source   │ 2. Build Pipeline (Ephemeral Worker)          │ 3. Output Targets   │
├───────────────────┼───────────────────────────────────────────────┼─────────────────────┤
│ 🐙 GitHub / GitLab│ ┌───────────────────────────────────────────┐ │ 📦 Artifact Registry│
│ 📁 Cloud Source   │ │ Step 1: Run Linter & Tests (python:3.11)  │ │    (Docker Images)  │
│ 🪝 Webhook / PubSub│ │                   │                       │ │ 🗄️ Cloud Storage   │
│ 💻 Manual Trigger │ │ Step 2: Build Container (gcr.io/cloud-buil-│ │    (Binaries/Zips) │
│                   │ │         ders/docker)                      │ │ 🚀 Deploy Targets │
│                   │ │                   │                       │ │    (Cloud Run/GKE)│
│                   │ │ Step 3: Push Image to Registry            │ │                     │
│                   │ └───────────────────────────────────────────┘ │                     │
└───────────────────┴───────────────────────────────────────────────┴─────────────────────┘

```

### 🔹 Core Architecture Components

1. 📂 **Source:** Code repository (GitHub, Bitbucket, GitLab, Cloud Storage bucket).
2. ⚡ **Trigger:** Event listener initiating a build on push, pull request, or tag.
3. ⚙️ **Build:** The execution instance containing one or more build steps.
4. 🧱 **Build Steps:** Independent commands running in isolated container environments.
5. 💻 **Worker:** The virtual environment (default shared pool or private pool) running the build.
6. 📦 **Artifacts:** Output packages pushed to registries or object storage.
7. 🚀 **Deployment:** Automated rollouts to compute environments.

## 3. `cloudbuild.yaml` Specification ⭐⭐⭐⭐⭐

The pipeline definition file instructing Cloud Build on what actions to take.

```yaml
steps:
  # Step 1: Run Unit Tests
  - name: 'python:3.11-slim'
    id: 'run-unit-tests'
    entrypoint: 'bash'
    args:
      - '-c'
      - |
        pip install -r requirements.txt
        pytest tests/
    env:
      - 'APP_ENV=test'

  # Step 2: Build Docker Image
  - name: 'gcr.io/cloud-builders/docker'
    id: 'build-image'
    args:
      - 'build'
      - '-t'
      - '$_LOCATION-docker.pkg.dev/$PROJECT_ID/$_REPO_NAME/order-api:$COMMIT_SHA'
      - '.'
    waitFor: ['run-unit-tests']

  # Step 3: Push to Artifact Registry
  - name: 'gcr.io/cloud-builders/docker'
    id: 'push-image'
    args:
      - 'push'
      - '$_LOCATION-docker.pkg.dev/$PROJECT_ID/$_REPO_NAME/order-api:$COMMIT_SHA'
    waitFor: ['build-image']

# Declare output images to track build provenance
images:
  - '$_LOCATION-docker.pkg.dev/$PROJECT_ID/$_REPO_NAME/order-api:$COMMIT_SHA'

# User-defined variables with default fallback values
substitutions:
  _LOCATION: 'us-central1'
  _REPO_NAME: 'apps'

# Overall build timeout
timeout: '1200s'

```

### 🔹 Key Directives Reference

* `steps`: List of containerized execution actions.
* `name`: The container image executing the step (e.g., `docker`, `gcloud`, `maven`, `golang`).
* `args`: Command-line arguments passed to the container's entrypoint.
* `env`: Environment variables passed to this specific step.
* `dir`: Working directory inside the workspace (defaults to `/workspace`).
* `id`: Unique identifier for the step (used to establish dependencies).
* `waitFor`: Defines execution order; lists step IDs that must complete first.
* `timeout`: Maximum run duration before the step/build is terminated.
* `substitutions`: Variables replaced dynamically at build runtime.
* `images`: Images pushed automatically upon build success and indexed in build logs.

---

## 4. Build Steps Execution Flow ⭐⭐⭐⭐⭐

### 🔹 Sequential vs. Parallel Execution

* **Sequential (Default):** If no `waitFor` is specified, steps execute strictly in order: Step 1 ➔ Step 2 ➔ Step 3.
* **Parallel Execution:** Use `waitFor: ['-']` to run a step immediately at the start in parallel with others:

```yaml
steps:
  # Runs immediately at start
  - name: 'node:20'
    id: 'frontend-tests'
    args: ['npm', 'test']
    waitFor: ['-']

  # Also runs immediately at start in parallel
  - name: 'golang:1.22'
    id: 'backend-tests'
    args: ['go', 'test', './...']
    waitFor: ['-']

  # Waits until BOTH frontend and backend tests pass
  - name: 'gcr.io/cloud-builders/docker'
    id: 'build-all'
    args: ['docker', 'build', '-t', 'my-image', '.']
    waitFor: ['frontend-tests', 'backend-tests']

```

## 5. Cloud Build Builders ⭐⭐⭐

A **Builder** is simply a container image pre-installed with tools:

* 🐳 **Official Google Builders:**
* `gcr.io/cloud-builders/docker`: Run Docker CLI commands.
* `gcr.io/cloud-builders/gcloud`: Run `gcloud` deployment and configuration commands.
* `gcr.io/cloud-builders/git`: Run version control operations.
* `gcr.io/cloud-builders/kubectl`: Deploy manifests to Kubernetes clusters.


* 🌐 **Public Open-Source Images:** Any image from Docker Hub (e.g., `maven:3.9`, `python:3.11`, `hashicorp/terraform:latest`, `node:20`).
* 🛠️ **Custom Builders:** You can build and push a custom Docker container containing proprietary tools to Artifact Registry and use it as a step `name`.

## 6. Cloud Build Triggers ⭐⭐⭐⭐⭐

A **Trigger** tells Cloud Build when to automatically run a build.

```
[ Developer Push / PR ] ──► [ Git Repository ] ──► [ Trigger Evaluator ] ──► [ Executes Build ]

```

### 🔹 Trigger Event Types

1. 🔀 **Push to a branch:** Executes whenever commits are pushed to branches matching a regex pattern (e.g., `^main$`, `^feature/.*`).
2. 📥 **Pull Request:** Runs checks and tests on open pull requests against a target branch.
3. 🏷️ **Push new tag:** Fires when a Git release tag is pushed (e.g., `v*.*.*`).
4. 🖱️ **Manual Invocations:** Triggered explicitly via Console, CLI, or API.
5. 📨 **Pub/Sub / Webhook Triggers:** Triggered by incoming event payloads from external platforms.

## 7. GitHub ➔ Cloud Build Integration Workflow ⭐⭐⭐⭐⭐

1. 🔗 **Connect Repository:**
* Go to **Cloud Build** ➔ **Repositories (2nd gen)**.
* Authenticate with GitHub via the Google Cloud Build GitHub App.
* Select target repositories.


2. ⚙️ **Create Trigger:**
* Set **Event** to *Push to a branch*.
* Set **Source branch regex** to `^main$`.
* Under **Configuration**, choose **Cloud Build configuration file (yaml or json)**.
* Provide the path: `cloudbuild.yaml`.


3. 🚀 **Execution:** Pushing code to GitHub automatically starts the build in Google Cloud Console.

## 8. Build Trigger Strategies & Environment Promotion ⭐⭐⭐⭐

```
[ Feature Branch ] ──► (PR Trigger)     ──► Run Linter & Unit Tests
        │
        ▼ Merge
[ Main / Develop ] ──► (Push Trigger)   ──► Build Image ➔ Deploy to Dev / Staging
        │
        ▼ Release Tag
[ Git Tag: v1.0.0 ]──► (Tag Trigger)    ──► Promote Image ➔ Deploy to Production

```

* **Branch Isolation:** Keep production and staging configurations isolated by mapping distinct triggers to specific branch regexes and variable substitutions.

```yaml
      - '-t'
      - 'us-central1-docker.pkg.dev/$PROJECT_ID/app-repo/web-service:latest'
      - '.'

  # Push both specific commit tag and latest tag
  - name: 'gcr.io/cloud-builders/docker'
    args:
      - 'push'
      - '--all-tags'
      - 'us-central1-docker.pkg.dev/$PROJECT_ID/app-repo/web-service'

```

## 10. Cloud Build + Artifact Registry ⭐⭐⭐⭐⭐

**Google Artifact Registry (GAR)** is the evolution of Container Registry (GCR):

```
Path Format:
[LOCATION]-docker.pkg.dev / [PROJECT_ID] / [REPOSITORY_NAME] / [IMAGE_NAME] : [TAG]
Example:
us-central1-docker.pkg.dev/prod-fleet-01/docker-repo/order-api:v1.2.0

```

* 🔑 **Authentication:** Cloud Build automatically authenticates with Artifact Registry within the same project through the default service account permissions.
* 🏷️ **Digest vs. Tag:**
* **Tag (`:v1.2.0`):** Human-readable pointer that can be overwritten.
* **Digest (`@sha256:7f8a...`):** Immutable cryptographic hash of the exact image contents, ensuring identical deployment across staging and production.

## 11. Non-Container Build Artifacts ⭐⭐⭐

Cloud Build is not limited to Docker images. It can compile and upload binaries, ZIP archives, or test coverage reports directly to **Cloud Storage (GCS)**:

```yaml
steps:
  # Compile static HTML/JS assets
  - name: 'node:20'
    args: ['npm', 'run', 'build']

# Upload the generated /dist folder directly to a GCS bucket
artifacts:
  objects:
    location: 'gs://my-app-static-assets-bucket/builds/$BUILD_ID'
    paths: ['dist/**']

```

## 12. Substitutions ⭐⭐⭐⭐

Substitutions allow you to parameterize your build configuration so values do not need to be hardcoded.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 🔄 Built-in Variables (Automatically Populated by GCP)                      │
├───────────────────┬─────────────────────────────────────────────────────────┤
│ `$PROJECT_ID`     │ Current GCP Project ID                                  │
│ `$BUILD_ID`       │ Unique ID generated for this specific build execution   │
│ `$COMMIT_SHA`     │ Complete Git commit SHA                                 │
│ `$SHORT_SHA`      │ First 7 characters of the commit SHA                    │
│ `$BRANCH_NAME`    │ Name of the Git branch triggering the build             │
│ `$TAG_NAME`       │ Name of the Git tag triggering the build                │
│ `$REPO_NAME`      │ Name of the source repository                           │
└───────────────────┴─────────────────────────────────────────────────────────┘

```

### 🔹 User-Defined Substitutions

Custom substitutions must begin with an underscore (`_`) when defined in triggers:

```yaml
steps:
  - name: 'gcr.io/cloud-builders/docker'
    args:
      - 'build'
      - '-t'
      - '$_REGION-docker.pkg.dev/$PROJECT_ID/$_REPO/api:$_ENV'
      - '.'

substitutions:
  _REGION: 'us-central1'
  _REPO: 'backend-services'
  _ENV: 'dev'

```

## 14. Secrets in Cloud Build ⭐⭐⭐⭐⭐

Never store plain-text credentials, database passwords, or private keys in `cloudbuild.yaml` or Git repositories. Retrieve them securely from **Secret Manager**.

```
[ Secret Manager ] ──► (Injected via IAM at runtime) ──► [ Cloud Build Step ]

```

```yaml
steps:
  - name: 'gcr.io/cloud-builders/gcloud'
    entrypoint: 'bash'
    args:
      - '-c'
      - |
        echo "Deploying with token..."
        curl -H "Authorization: Bearer $$DEPLOY_TOKEN" https://api.example.com/deploy
    secretEnv: ['DEPLOY_TOKEN']

availableSecrets:
  secretManager:
    - versionName: projects/$PROJECT_ID/secrets/my-deploy-token/versions/latest
      env: 'DEPLOY_TOKEN'

```

## 15. Cloud Build IAM Roles & Permissions ⭐⭐⭐⭐

Cloud Build uses a dedicated Service Account to execute tasks:

* 🤖 **Default Service Account:** `[PROJECT_NUMBER]@cloudbuild.gserviceaccount.com` (Legacy) or user-managed Service Accounts (Modern standard).

```
┌──────────────────────────────────────┬──────────────────────────────────────────────────────────┐
│ Required IAM Role                    │ Action Enabled                                           │
├──────────────────────────────────────┼──────────────────────────────────────────────────────────┤
│ `roles/artifactregistry.writer`      │ Push Docker images to Artifact Registry                  │
│ `roles/run.admin`                    │ Deploy new revisions to Cloud Run                        │
│ `roles/iam.serviceAccountUser`       │ Act as the Cloud Run runtime Service Account             │
│ `roles/container.developer`          │ Deploy manifests to Google Kubernetes Engine (GKE)       │
│ `roles/secretmanager.secretAccessor` │ Access sensitive secrets during build execution          │
└──────────────────────────────────────┴──────────────────────────────────────────────────────────┘

```

## 16. Secure Build Pipeline & Supply Chain Security ⭐⭐⭐⭐

```
[ Verified Source ] ──► [ Build Container ] ──► [ Vulnerability Scan ] ──► [ Signed Artifact ]

```

1. 🛡️ **Least Privilege:** Use user-managed service accounts tailored to specific triggers rather than granting broad project-level permissions.
2. 🔍 **Container Analysis / Vulnerability Scanning:** Enable automatic vulnerability scanning in Artifact Registry on image push.
3. 🔏 **Binary Authorization (SLSA Level 3):** Sign container images during build time with Cloud KMS keys to ensure only approved images deploy to production.

## 21. Default Shared Pools vs. Private Pools ⭐⭐⭐

```
┌──────────────────────────────────────┬──────────────────────────────────────────────────────────┐
│ Feature                              │ Default Pool (Shared)      │ Private Pool (Dedicated)   │
├──────────────────────────────────────┼────────────────────────────┼──────────────────────────┤
│ 🌐 Network Access                    │ Public Internet Only       │ Internal VPC Peering     │
│ 💻 Machine Sizes                     │ Standard (1–32 vCPUs)      │ Configurable / High-CPU  │
│ 🔒 Isolation                         │ Multi-tenant VM sandboxes  │ Single-tenant hosted VMs │
│ 💰 Pricing Model                     │ Pay-per-build-minute       │ Billed for worker uptime │
└──────────────────────────────────────┴────────────────────────────┴──────────────────────────┘

```

* **When to use Private Pools:** When builds must access internal databases, private on-premise Git servers, or custom internal package repositories without traversing the public internet.

## 23. Parallel Step Execution via `waitFor` ⭐⭐⭐⭐

```
[ Start ] ──┬──► Step: Lint Code (waitFor: ['-']) ──────────┐
            ├──► Step: Frontend Unit Tests (waitFor: ['-']) ─┼──► Step: Build Final Docker Image
```

## 26. Build Failure Troubleshooting Matrix ⭐⭐⭐⭐⭐

```
┌───────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────┐
│ Error / Failure Point     │ Primary Root Cause               │ Remediation / Fix                        │
├───────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────┤
│ 🚫 Permission Denied (403)│ Service Account lacks IAM roles  │ Grant `roles/artifactregistry.writer` or │
│                           │                                  │ `roles/run.admin` to Cloud Build SA      │
├───────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────┤
│ 📜 YAML Syntax Failure    │ Bad indentation, invalid keys    │ Run `cloud-build-local` or lint YAML     │
├───────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────┤
```

## 30. Cloud Build Definitions & Fundamentals

* 🎙️ **What is Google Cloud Build?**
> "A fully managed, serverless CI/CD service that runs each step of a build pipeline as a separate Docker container, scaling resources automatically without requiring build master management."



---

## 31. Cloud Build Architecture Questions

* 🎙️ **How does workspace sharing work between steps?**
> "Cloud Build automatically mounts a shared volume at `/workspace` across all steps in the build. Files created or modified in `/workspace` during Step 1 are directly accessible to subsequent steps."



---

## 32. `cloudbuild.yaml` Execution Questions

* 🎙️ **How do you make Step 2 and Step 3 run in parallel right at the start?**
> "By adding `waitFor: ['-']` to both Step 2 and Step 3. This overrides the default sequential behavior and instructs Cloud Build to launch both containers concurrently at $t=0$."



---

## 33. Trigger & Source Management Questions

* 🎙️ **How do you trigger a build only when specific files change (e.g., frontend code only)?**
> "Use **Included Files** (file filters) in the trigger configuration, specifying glob patterns like `frontend/**`. Changes to backend files will be ignored."



---

## 34. Docker & Artifact Registry Questions

* 🎙️ **Why should production CD pipelines deploy by image digest (`@sha256:...`) instead of image tag (`:latest`)?**
> "Image tags are mutable and can be overwritten. Deploying by the immutable SHA256 digest guarantees that the exact binary that passed staging tests is what gets deployed to production, preventing supply-chain drift."



---

## 35. Cloud Build + Cloud Run Integration Questions

* 🎙️ **What IAM roles does Cloud Build need to deploy a Cloud Run service?**
> "The Cloud Build Service Account requires:
> 1. `roles/run.admin` (to create/update Cloud Run revisions).
> 2. `roles/iam.serviceAccountUser` (to act as the runtime service account attached to Cloud Run)."
> 
> 



---

## 36. Cloud Build + GKE Deployment Questions

* 🎙️ **How do you securely deploy to a Private GKE Cluster from Cloud Build?**
> "Deploy using a **Cloud Build Private Pool** peered with the VPC where the private GKE cluster's control plane endpoint resides, or authorize Cloud Build public IP ranges on the master authorized networks."



---

## 37. IAM & Security Questions

* 🎙️ **Should you use the default Cloud Build Service Account for production deployments?**
> "No. Follow the principle of least privilege by configuring a dedicated, user-managed Service Account per pipeline trigger, granting only the specific permissions needed for those build steps."



---

## 38. Secret Management Questions

* 🎙️ **How do you prevent secrets from leaking into build step logs?**
> "Use the native `availableSecrets` block referencing Secret Manager and map them using `secretEnv`. Prefix environment variables with double dollar signs (`$$SECRET_VAR`) inside execution scripts so they aren't expanded into build logs."



---

## 39. Enterprise Production Scenarios

* 🎙️ **How do you implement an emergency rollback in Cloud Build?**
> "Maintain an immutable record of previously deployed revision tags or digests. Re-trigger a deployment build step pointing to the known stable container digest, or use `gcloud run services update-traffic` to point 100% of traffic back to the previous healthy revision."



---

## 40. Troubleshooting Playbook

* 🎙️ **What steps do you take when a build fails with `Error response from daemon: unauthorized: You don't have permission to write to Artifact Registry`?**
> "1. Check the Service Account executing the build.
> 2. Verify that `roles/artifactregistry.writer` is bound to that service account on the target repository or project.
> 3. Ensure the Artifact Registry API is enabled."
