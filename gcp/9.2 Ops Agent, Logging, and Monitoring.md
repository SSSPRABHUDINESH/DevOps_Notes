# 🟦 PART A — OBSERVABILITY FUNDAMENTALS

---

## 1. Observability Fundamentals ⭐⭐⭐⭐⭐

### 🔹 Monitoring vs. Logging vs. Observability

* 📊 **Monitoring (The "What"):** Tells you *that* a system is broken or degraded (e.g., "CPU utilization is at 95%"). It tracks known failure modes.
* 📜 **Logging (The "Why"):** Provides a chronological record of discrete events (e.g., "Database connection timeout at 14:02:01").
* 🔍 **Observability (The "How"):** The property of a system that allows you to infer its internal state purely by observing its external outputs (metrics, logs, and traces). It enables debugging *unknown* failure modes.

```
┌────────────────────────────────────────────────────────┐
│               Observability Pillars 🏛️                │
├───────────────────┬────────────────────┬───────────────┤
│    Metrics 📈     │      Logs 📜       │   Traces ⏱️   │
│ Aggregated numbers│ Timestamped event  │ Request paths │
│   over time       │     records        │  across hops  │
└───────────────────┴────────────────────┴───────────────┘

```

---

### 🔹 The Four Golden Signals (SRE Standard)

1. ⏱️ **Latency:** The time it takes to service a request (differentiating between successful and failed request latency).
2. 🚦 **Traffic:** A measure of system demand (e.g., HTTP requests per second, I/O operations per second).
3. ❌ **Errors:** The rate of requests that fail (e.g., HTTP 5xx responses, exception counts).
4. 🎚️ **Saturation:** How "full" the service is, measuring constrained resources (e.g., memory usage, thread pool saturation, CPU throttle limits).

---

### 🔹 Service Level Terminology: SLI vs. SLO vs. SLA

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 📐 SLI (Indicator): What you measure   ➔ "Successful HTTP requests / Total"│
│ 🎯 SLO (Objective): Internal target    ➔ "99.9% success rate per 30 days"   │
│ ⚖️ SLA (Agreement): Business contract  ➔ "99.5% or customer gets a refund" │
└─────────────────────────────────────────────────────────────────────────────┘

```

## 2. Google Cloud Operations Suite Overview ⭐⭐⭐⭐

Google Cloud Operations (formerly Stackdriver) unifies monitoring, logging, and performance management:

* 📈 **Cloud Monitoring:** Tracks infrastructure metrics, uptime, dashboards, and automated alert policies.
* 📜 **Cloud Logging:** Ingests, stores, searches, analyzes, and routes log events at scale.
* ⏱️ **Cloud Trace:** Distributed tracing system that collects latency data from applications to display per-request waterfalls.
* 🚨 **Error Reporting:** Automatically groups application stack traces and unhandled exceptions by error type.
* 🔬 **Cloud Profiler:** Continuous CPU and memory profiling tool to identify code-level performance bottlenecks.

## 3. Cloud Monitoring Fundamentals ⭐⭐⭐⭐⭐

### 🔹 Anatomy of a Metric

Cloud Monitoring stores metric data as **Time Series**:

* 🏷️ **Metric Type:** Identifies what is being measured (e.g., `[compute.googleapis.com/instance/cpu/utilization](https://compute.googleapis.com/instance/cpu/utilization)`).
* 🖥️ **Monitored Resource Type:** Identifies the source of data (e.g., `gce_instance`, `cloud_run_revision`).
* 📌 **Labels:** Key-value pairs providing dimensional metadata (e.g., `instance_id`, `zone`, `project_id`).
* 📊 **Metric Points:** Pairs of timestamps and measured numeric values.

```
Metric: compute.googleapis.com/instance/cpu/utilization
Resource: gce_instance (zone="us-central1-a", instance_id="384910293")
Points: [ (10:00, 0.42), (10:01, 0.45), (10:02, 0.89) ]

```

---

## 4. GCP Metrics & Metric Types ⭐⭐⭐⭐⭐

### 🔹 Categories of Metrics

* 🌐 **System / Google Cloud Service Metrics:** Ingested automatically without any agent from Google-managed services (Cloud SQL, BigQuery, Load Balancers).
* 🖥️ **Agent-Based Metrics:** Ingested from operating systems and standard software via the **Ops Agent**.
* ⚙️ **Custom / User-Defined Metrics:** Custom data points pushed directly by application code using the Cloud Monitoring API or OpenTelemetry.

---

### 🔹 Value Types & Metric Kinds

| Metric Kind | Description | Example |
| --- | --- | --- |
| **GAUGE** | An instantaneous measurement at a specific point in time. | Current RAM utilization (65%), CPU temperature. |
| **DELTA** | The change in a value over a specific time window. | Received bytes in the last 60 seconds. |
| **CUMULATIVE** | A value that monotonically increases over time. | Total requests served since the VM booted. |

## 7. Metrics Explorer ⭐⭐⭐⭐⭐

**Metrics Explorer** allows interactive investigation of time-series data:

1. 📍 **Resource Selection:** Select resource type (e.g., `VM Instance`).
2. 📊 **Metric Selection:** Select the target metric (e.g., `CPU utilization`).
3. 🔍 **Filter:** Narrow by labels (e.g., `metadata.system_labels.environment = "production"`).
4. ⚙️ **Aggregation & Alignment:**

5. 🔀 **Group By:** Group time-series curves by specific labels (e.g., `zone` or `instance_group`).

## 8. What is Google Cloud Ops Agent? ⭐⭐⭐⭐⭐

The **Google Cloud Ops Agent** is the unified agent for Compute Engine instances. It combines logging and metrics collection into a single, high-performance binary:

```
┌─────────────────────────────────────────────────────────────┐
│                      OPS AGENT Process                      │
│                                                             │
│  📜 Fluent Bit Engine        📊 OpenTelemetry Collector     │
│  (High-throughput Logging)    (Lightweight Metric Scraper)  │
└──────────────┬──────────────────────────────┬───────────────┘
               ▼                              ▼
      [ Cloud Logging ]              [ Cloud Monitoring ]

```

* **Replaces Legacy Agents:** Supersedes both the legacy Stackdriver Logging Agent (`fluentd`) and Monitoring Agent (`collectd`).

---

## 9. Ops Agent Architecture ⭐⭐⭐⭐⭐

```
[ Log Files / Syslog ] ──► [ Receiver ] ──► [ Processor / Parser ] ──► [ Exporter ] ──► Cloud Logging
[ Host / App Metrics ] ──► [ Receiver ] ──► [ Processor / Aligner ] ──► [ Exporter ] ──► Cloud Monitoring

```

1. 📥 **Receivers:** Ingest raw telemetry from file logs, `journald`, syslog, or system performance counters.
2. ⚙️ **Processors:** Parse unstructured text into structured JSON, modify timestamps, and enrich labels.
3. 📤 **Exporters:** Securely transmit telemetry batches to Google Cloud APIs.

## 11. Ops Agent Configuration (`config.yaml`) ⭐⭐⭐⭐⭐

The configuration file is located at `/etc/google-cloud-ops-agent/config.yaml`.

### 🔹 Structure of `config.yaml`

```yaml
logging:
  receivers:
    syslog:
      type: files
      include_paths:
        - /var/log/syslog
        - /var/log/messages
    app_log:
      type: files
      include_paths:
        - /var/log/my-app/*.log
  processors:
    app_parser:
      type: json_parser
      time_key: time
      time_format: "%Y-%m-%dT%H:%M:%S%z"
  service:
    pipelines:
      default_pipeline:
        receivers: [syslog, app_log]
        processors: [app_parser]

metrics:
  receivers:
    hostmetrics:
      type: hostmetrics
      collection_interval: 60s
  service:
    pipelines:
      default_pipeline:
        receivers: [hostmetrics]

```

```bash
# Validate and restart after updating configuration
sudo systemctl restart google-cloud-ops-agent

```

## 12. Ops Agent Logging Pipeline ⭐⭐⭐⭐⭐

* **File Receivers:** Tail application files using glob patterns (`/opt/app/logs/*.log`).
* **System Receivers:** Capture `systemd-journald` output and standard OS messages.
* **Processors / Parsers:** Convert unstructured text to structured JSON payloads so fields can be queried in Cloud Logging.

---

## 13. Ops Agent Metrics Pipeline ⭐⭐⭐⭐⭐

* **Host Metrics:** Collects OS-level memory usage, swap space, disk partition capacities (`/`, `/var`, `/home`), network socket states, and per-process resource consumption.
* **Third-Party Integrations:** Built-in scrapers available for common software (Nginx, Apache, MySQL, PostgreSQL, Redis, JVM) without writing custom exporter code.

---

## 14. Custom Application Logs & Structured JSON ⭐⭐⭐⭐

When application code writes logs directly in JSON to stdout or log files, Ops Agent transmits them as a **`jsonPayload`**:

  "message": "Payment processing failed for customer",

---

## 15. Custom Application Metrics & Cardinality ⭐⭐⭐⭐

* **OpenTelemetry Support:** Applications push custom metric data points directly to the Ops Agent local OTLP port.
* ⚠️ **Managing Metric Cardinality:**
* **Low Cardinality (Good):** Labels with bounded values (e.g., `environment: ["prod", "stage"]`, `http_status: [200, 404, 500]`).
* **High Cardinality (Dangerous):** Labels with infinite unique values (e.g., `user_id`, `order_id`, `email`). This creates millions of individual time series, causing unexpected Cloud Monitoring costs.

## 20. Log Router & Storage ⭐⭐⭐⭐

The Log Router in [Google Cloud](https://cloud.google.com/) is the central engine that receives every log entry sent to the Cloud Logging API and determines exactly where it should go. Think of it as a traffic controller for your logs—it intercepts data in real-time, checks it against specific rules, and forwards it to its final destination.
## How the Log Router Works

* **Ingestion:** Services (like Compute Engine, Cloud Run, or GKE) send their logs directly to the Cloud Logging API.
* **Evaluation:** The Log Router checks each incoming log entry against your configured Log Sinks.
* **Routing:** Based on those sinks' filters, the Log Router duplicates or redirects the logs to storage, BigQuery, Pub/Sub, or other destinations.

## Default Routes Created Automatically
By default, the Log Router automatically creates two sinks for every new Google Cloud project to handle standard logging traffic:

* **_Required:** Routes critical platform logs (like Admin Activity Audit Logs) to a hidden storage bucket. These logs are stored for 400 days and cannot be disabled, modified, or deleted.
* **_Default:** Routes all other project logs to a standard storage bucket for 30 days. This sink can be edited, disabled, or paused if you want to stop storing standard logs in Cloud Logging to save on costs.

```
┌─────────────────┬───────────────────┬───────────────────────────────────────────┐
│ Log Bucket      │ Default Retention │ Purpose                                   │
├─────────────────┼───────────────────┼───────────────────────────────────────────┤
│ `_Required`     │ 400 Days          │ Admin Activity Audit Logs (Free & Locked) │
│ `_Default`      │ 30 Days           │ General application and resource logs     │
│ `User-Defined`  │ 1 to 3650 Days    │ Custom retention and compliance storage   │
└─────────────────┴───────────────────┴───────────────────────────────────────────┘

```

## 21. Log Sinks ⭐⭐⭐⭐⭐

A log sink in Google Cloud Logging is a tool used by the [Log Router](https://docs.cloud.google.com/logging/docs/routing/overview) to route and export log entries to specific destinations. [1] 
## Key Functions of a Log Sink

* Filtering: Uses inclusion and exclusion filters to decide which log entries to route and which to ignore.
* Routing: Sends matching logs to a chosen destination instead of just the default storage.
* Control: Operates at the project, folder, billing account, or organization level. [1] 

## Supported Destinations

* **Cloud Logging Log Buckets:** Custom storage buckets within Google Cloud for analysis.
* **BigQuery:** Datasets for running SQL queries and deep data analysis.
* **Cloud Storage:** Buckets for long-term archiving as JSON files.
* **Pub/Sub:** Topics for streaming logs to external applications or third-party tools.
* **Other Projects:** Centralized logging projects to aggregate data across an organization. [1, 2, 3, 4, 5] 

```
                       ┌──► 🗄️ Cloud Storage (Long-term Cold Compliance Archive)
                       │
[ Log Router / Sink ] ─┼──► 📊 BigQuery (SQL Analysis & Analytics)
                       │
                       ├──► 📨 Pub/Sub (Export to Splunk, Datadog, or SIEM)
                       │
                       └──► 📦 Central Log Bucket (Cross-Project Aggregation)

```

```bash
# Create a Log Sink that exports error logs to a Cloud Storage bucket
gcloud logging sinks create storage-error-sink \
    storage.googleapis.com/my-security-archive-bucket \
    --log-filter='severity>=ERROR'

```

## 23. Cloud Audit Logs ⭐⭐⭐⭐⭐

Google Cloud Audit Logs maintain an immutable security ledger recording **who did what, where, and when** across your GCP environment.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                            CLOUD AUDIT LOGS 🛡️                              │
├────────────────────┬────────────────────┬─────────────────┬─────────────────┤
│ 🔨 Admin Activity  │ 👁️ Data Access     │ ⚙️ System Event │ 🚫 Policy Denied│
│ (Resource Config)  │ (Reading Data)     │ (GCP Automation)│ (IAM / VPC-SC)  │
│ - Created VM       │ - Read GCS Object  │ - Auto-restart  │ - Org Policy or │
│ - Modified Firewall│ - Queried Cloud SQL│ - Instance heal │   VPC-SC blocked│
│ - Deleted Database │ - Read Secret Mgr  │ - GCP patch     │   an action     │
│ ------------------ │ ------------------ │ --------------- │ --------------- │
│ ✅ Enabled 24/7    │ ⚠️ Off by default  │ ✅ Enabled 24/7 │ ✅ Enabled 24/7 │
│ 🆓 Always Free     │ 💰 Storage costs   │ 🆓 Always Free  │ 🆓 Always Free  │
│ 📅 400 Days Store  │ 📅 30 Days default │ 📅 400 Days     │ 📅 400 Days     │
└────────────────────┴────────────────────┴─────────────────┴─────────────────┘

```

### 🔹 The 4 Core Forensic Questions Answered by Audit Logs

Every Audit Log record formats into a standardized `protoPayload`:

* 👤 **Who?** (`protoPayload.authenticationInfo.principalEmail`): The identity (human or Service Account) executing the request.
* 🛠️ **What?** (`protoPayload.methodName`): The exact API action executed (e.g., `v1.compute.firewalls.delete`).
* 📍 **On which resource?** (`protoPayload.resourceName`): The targeted cloud resource URI.
* ⏱️ **When?** (`timestamp`): UTC timestamp down to the microsecond.

## 25. Alerting Fundamentals & Lifecycle ⭐⭐⭐⭐⭐

An **Alerting Policy** continuously evaluates time-series metric data or incoming log patterns to automatically trigger notifications when unhealthy anomalies occur.

```
[ Metric Data / Logs ] ──► [ Condition Evaluator ] ──► [ Threshold Breached for Duration ]
                                                                     │
                                                                     ▼
                                                          🚨 [ Incident Opened ]
                                                                     │
                                                                     ▼
                                                      📢 [ Notification Dispatched ]
                                                          (Slack / PagerDuty / Email)
                                                                     │
                                                      [ Metric Returns to Normal ]
                                                                     │
                                                                     ▼
                                                          ✅ [ Incident Resolved ]

```

### 🔹 Core Anatomy of an Alert

1. 🎯 **Condition:** The metric being evaluated (e.g., `[compute.googleapis.com/instance/cpu/utilization](https://compute.googleapis.com/instance/cpu/utilization)`).
2. 🎚️ **Threshold:** The boundary value (e.g., `> 0.85` or 85%).
3. ⏱️ **Duration / Window:** How long the metric must stay above the threshold before triggering (e.g., *“for at least 5 consecutive minutes”*). This prevents alerts on harmless 2-second spikes.
4. 🔀 **Trigger Strategy:** Trigger when **any** time series violates the condition, or when a **percentage** of instances violate it.
5. 📂 **Incident & Notification Channel:** Automatically groups alerts into an incident and pages on-call engineers.

---

## 26. Metric-Based Alerts ⭐⭐⭐⭐⭐

Common production metric alerts:

* 💻 **Host CPU Utilization:** Alert if CPU $> 85\%$ for $10\text{ minutes}$.
* 🧠 **Guest Memory Utilization:** Alert if RAM $> 90\%$ for $5\text{ minutes}$ (requires Ops Agent).
* 💽 **Disk Space Consumption:** Alert if `/` volume free space $< 15\%$.
* ❌ **HTTP 5xx Error Rate:** Alert if $5\text{xx errors} > 2\%$ of total requests on a Load Balancer or Cloud Run.
* ⏱️ **Request Latency (p99):** Alert if 99th percentile response time $> 1500\text{ ms}$.

---

## 27. Log-Based Alerts ⭐⭐⭐⭐⭐

Trigger alerts immediately when critical log patterns arrive in Cloud Logging without waiting for metric aggregation:

```sql
-- Example Log Alert Query: Detect unauthorized database login attempts
resource.type="cloudsql_database"
severity >= WARNING
textPayload =~ "Access denied for user"

```

* **Best Use Cases:** Security breaches, application fatal exceptions, panics, or license expiration warnings.

## 29. Alert Design Best Practices & Eliminating Fatigue ⭐⭐⭐⭐⭐

* 🔔 **Alert on Symptoms, Not Causes:**
* *Poor Alert:* "Host 04 CPU is 92%" (User might not be impacted).
* *Good Alert:* "Checkout API 5xx Error Rate $> 1\%$ for $3\text{ minutes}$" (Direct user impact).


* ⏱️ **Tune Durations:** Avoid zero-duration alerts. Spikes happen during garbage collection or cron jobs; require the failure to persist across a duration (e.g., $5\text{ minutes}$).
* 🏷️ **Include Runbooks / Actionable Documentation:** Every alert payload should contain a direct link to a runbook:
* *"Step 1: Run `systemctl restart backend`. Step 2: Check database connection pool."*

## 30. Uptime Checks ⭐⭐⭐⭐

**Uptime Checks** run synthetic probes from multiple servers located worldwide (e.g., USA, Europe, Asia-Pacific) to verify that your service is reachable from the public internet.

```
[ USA Probe ] ────┐
[ Europe Probe ] ─┼──► ( Every 1 min ) ──► [ https://api.mycompany.com/healthz ]
[ Asia Probe ] ───┘

```

* 🌐 **Supported Protocols:** HTTP, HTTPS, and TCP.
* ✅ **Response Validation:** Validates HTTP status code (`200 OK`) and checks for specific response body strings (e.g., `{"status": "UP"}`).
* 🚨 **Global Outage Detection:** If 2 or more regions report failure simultaneously, an uptime alert triggers immediately.

## 31. Application Performance Monitoring (APM) ⭐⭐⭐⭐

* ⏱️ **Cloud Trace (Distributed Tracing):** Tracks how a user request flows through microservices. It highlights which microservice or database query added latency.

```
[ User Request ] ──► [ Frontend Service (40ms) ]
                               │
                               ├──► [ Auth Service (15ms) ]
                               │
                               └──► [ Payment API (850ms) ] ──► [ Cloud SQL Query (820ms) ⚠️ Bottleneck ]

```

* 📈 **Latency Percentiles (p50, p95, p99):**
* **p50 (Median):** Half of users experience faster response times than this value.
* **p99 (Tail Latency):** $1\%$ of users experience this slow performance. This is the metric enterprise SLAs focus on optimizing.

## 49. High CPU Production Incident Response ⭐⭐⭐⭐⭐

* 🛠️ **Remediation Procedure:**

5. Check recent application logs for infinite retry loops or unhandled tasks.

## 59. Troubleshooting Scenarios: "Deleted Files Still Consuming Disk"

* ❓ **"Why did running `rm` on a 20GB log file not reclaim disk space on Linux?"**
* *Answer:* A running process still holds an open file descriptor to the deleted inode. Linux unlinks the filename from the directory structure, but keeps the disk blocks allocated until the process terminates.
* *Resolution:* Run `sudo lsof | grep deleted` to identify the PID, then restart the associated system service to release the disk blocks.
