# Technical Reference: Secrets vs. Variables, Secret Masking, GITHUB_TOKEN & GitHub App Security

---

## 1. Secrets vs. Variables: Scope & Resolution Hierarchy

GitHub Actions differentiates between non-sensitive configuration values (**Variables**) and encrypted credentials (**Secrets**).

### Scope Hierarchy & Resolution Precedence

When a key exists in multiple scopes, GitHub Actions resolves values using a strict **top-down precedence rule** (most specific scope wins):

```text
               RESOLUTION PRECEDENCE (Top Down):
               
         ┌──────────────────────────────────────────┐
         │ 1. Environment Scope                     │  (Highest Priority - Overrides all)
         │    secrets.MY_KEY / vars.MY_KEY          │
         └────────────────────┬─────────────────────┘
                              │
                              ▼
         ┌──────────────────────────────────────────┐
         │ 2. Repository Scope                      │
         │    secrets.MY_KEY / vars.MY_KEY          │
         └────────────────────┬─────────────────────┘
                              │
                              ▼
         ┌──────────────────────────────────────────┐
         │ 3. Organization Scope                    │  (Lowest Priority)
         │    secrets.MY_KEY / vars.MY_KEY          │
         └──────────────────────────────────────────┘

```

### Architectural Comparison Matrix

| Dimension | Variables (`vars.KEY`) | Secrets (`secrets.KEY`) |
| --- | --- | --- |
| **Storage & Encryption** | Stored as plain text. | Encrypted at rest using libsodium sealed boxes before being stored in GitHub DB. |
| **Workflow Access** | Directly accessed via standard context syntax `vars.PORT_NUMBER`. | Access context: `secrets.API_TOKEN`. Decrypted **only when injected into runner memory**. |
| **Log Masking** | **None.** Output to console appears in raw plain text. | **Automatic.** Replaced with `***` across all stdout/stderr logs. |
| **Pull Requests from Forks** | Available to fork PR workflows if permitted. | **Blocked by default** from fork PR runs to prevent credential theft. |
| **Best Used For** | Non-sensitive configs (domain names, ports, regions, flag toggles). | Cloud credentials, private SSH keys, DB passwords, API tokens. |

## 2. Deep-Dive: Secret Masking Mechanics & Evasion Pitfalls

### How the Runner Masker Engine Works

When a job starts, the runner collects all resolved secrets for that job and registers their string values with an internal **log obfuscation engine**.

Any text emitted to `stdout` or `stderr` is scanned against this list of registered secrets before being streamed back to GitHub servers. Every exact string match is scrubbed and printed as `***`.

```text
[Runner Process Engine]
      │
      ├─► Step output: "Connecting to https://api.site.com with token secret_pass_123"
      │
      ▼
[Log Masking Filter Engine (Exact String Matcher)]
      │
      ├─► Matches "secret_pass_123"
      │
      ▼
[Console Stream Payload] ──► "Connecting to https://api.site.com with token ***"

```

### Manual Masking via Workflow Commands (`::add-mask::`)

If a workflow dynamically generates or fetches a secret during step execution (e.g., retrieving an API key via `curl` or OIDC), it **will not be masked automatically** because the runner did not know the value prior to step execution. You must register it manually using the `::add-mask::` workflow command.

```yaml
      - name: Fetch Dynamic Secret and Mask
        run: |
          # Fetch secret token dynamically
          DYNAMIC_TOKEN=$(curl -s https://api.example.com/token)

          # 1. Register with runner log masker immediately
          echo "::add-mask::$DYNAMIC_TOKEN"

          # 2. Export to environment for subsequent steps
          echo "DYNAMIC_TOKEN=$DYNAMIC_TOKEN" >> $GITHUB_ENV

```

### ⚠️ Log Leakage Evasion Edge-Cases (Why Masking Fails)

1. **Transformed / Encoded Data:** If a secret string (`my_secret_123`) is base64-encoded (`bXlfc2VjcmV0XzEyMw==`), URL-encoded, or JSON-stringified with escapes, the runner's exact-match engine will **fail to match it**, printing the encoded secret in raw text.
2. **Short / Common Strings:** Secrets shorter than 3-4 characters (or common words like `admin`) cause mass over-redaction, obscuring standard log text across the entire build.
3. **Structured Payload Printing:** Echoing full JSON/YAML payloads (e.g., `echo "$JSON_RESPONSE"`) containing nested secret values can expose partial string fragments if line feeds or formatting alter the exact byte sequence.

## 3. `GITHUB_TOKEN` Security & Explicit Permission Scopes

Every GitHub Actions job automatically receives a ephemeral `GITHUB_TOKEN` (via `secrets.GITHUB_TOKEN`) to authenticate API operations on behalf of the workflow.

### The Security Vulnerability: Permissive Defaults

* **Default Org Setting (Legacy):** Read/Write access across all resources (repositories, packages, contents, checks). If a dependency script or third-party Action is compromised, an attacker can push code directly to `main` or alter releases using the default token.
* **Hardened Org Setting (Production Standard):** Restrict default workflow permissions to **Read-only** across all organizations.

```yaml
# Settings -> Actions -> General -> Workflow permissions:
# Select: "Read repository contents and packages permissions"

```

### Explicit Permission Block Invocations

Applying the top-level or job-level `permissions` block **revokes all default access** and grants *only* the scopes explicitly declared. Undefined scopes default to `none`.

```yaml
name: Security-Hardened Pipeline

on:
  push:
    branches: [ main ]

# Explicitly strip all default permissions globally across the workflow
permissions: {}

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    permissions:
      contents: read     # Required to checkout repository code
      security-events: write # Required to upload SARIF security scan results

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Run CodeQL Analysis
        uses: github/codeql-action/analyze@v3

  create-release:
    needs: build-and-test
    runs-on: ubuntu-latest
    permissions:
      contents: write    # Grants permission to create git tags/releases
      issues: write      # Grants permission to close related deployment issues

    steps:
      - name: Create GitHub Release
        run: gh release create v1.0.0 --title "Release v1.0.0"
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

```

### Permission Matrix Quick-Reference

| Scope Name | Read Level | Write Level | Common Use Case |
| --- | --- | --- | --- |
| `contents` | Read code/commits | Push commits, create tags | Code checkout vs. Automated release tags |
| `packages` | Pull container images | Publish npm/Docker images | CI build vs. Registry publishing |
| `pull-requests` | View PR metadata | Add comments, merge PRs | PR bot comments, auto-merging |
| `id-token` | N/A | Request OIDC JWT | Cloud authentication (AWS, GCP, Vault) |
| `security-events` | Read security alerts | Write/Upload SARIF data | SonarQube, Trivy, CodeQL scan uploads |

## 4. GitHub App Authentication Patterns

### Why Replace Personal Access Tokens (PATs) with GitHub Apps?

| Feature | Personal Access Token (PAT) | GitHub App Installation Token |
| --- | --- | --- |
| **Identity Type** | Bound to an individual human user account. | Non-human machine identity owned by the Org. |
| **User Offboarding** | If the user leaves the company, their PATs break all CI pipelines. | Pipelines remain completely unaffected. |
| **Scope Boundary** | Access to **ALL** repos the user can access (Excessive Privilege). | Fine-grained, restricted to **only specific selected repos**. |
| **Event Triggers** | Actions triggered by a PAT **will trigger** secondary workflows. | Actions performed by `GITHUB_TOKEN` or GitHub Apps **do not** cause recursive loops. |
| **Token Lifespan** | Long-lived (30, 60, 90 days, or non-expiring). | Short-lived installation token (**expires in 1 hour**). |

---

### Step-by-Step GitHub App Authentication Workflow

To authenticate a workflow using a GitHub App, use `actions/create-github-app-token` to exchange the App's Private Key and App ID for a short-lived token.

```text
┌────────────────────────┐      1. Authenticate with App ID + Private Key       ┌────────────────────────┐
│ GitHub Actions Runner  │ ───────────────────────────────────────────────────► │ GitHub Apps API        │
└───────────┬────────────┘                                                      └───────────┬────────────┘
            │                                                                               │
            │ 2. Issues 1-Hour Installation Access Token                                    │
            ◄───────────────────────────────────────────────────────────────────────────────┘
            │
            ▼
┌────────────────────────┐
│ Step Execution         │ ───► Uses temporary token to access cross-repo contents or trigger workflows
└────────────────────────┘

```

#### Production Workflow Syntax

```yaml
name: Cross-Repository Release Orchestrator

on:
  push:
    branches: [ main ]

jobs:
  trigger-downstream-build:
    runs-on: ubuntu-latest
    steps:
      - name: Generate GitHub App Token
        id: generate_token
        uses: actions/create-github-app-token@v1
        with:
          app-id: ${{ secrets.BOT_APP_ID }}
          private-key: ${{ secrets.BOT_PRIVATE_KEY }}
          owner: ${{ github.repository_owner }}
          repositories: "infrastructure-manifests,payment-service"

      - name: Dispatch Event to Infrastructure Repo
        run: |
          # Use generated token to trigger repository_dispatch event in a separate repo
          curl -X POST \
            -H "Authorization: Bearer ${{ steps.generate_token.outputs.token }}" \
            -H "Accept: application/vnd.github.v3+json" \
            https://api.github.com/repos/${{ github.repository_owner }}/infrastructure-manifests/dispatches \
            -d '{"event_type": "app_deployed"}'

```
