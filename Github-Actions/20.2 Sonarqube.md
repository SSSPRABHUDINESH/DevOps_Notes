## SonarQube 

SonarQube acts as an automated "Code Reviewer" in your CI/CD pipeline. While **GitHub Actions** handles running jobs, **SonarQube** performs static code analysis to check for bugs, vulnerabilities, and code smell before code reaches production.

---

### Core Concepts

* **Code Issues:**
* **Bugs:** Errors that will break code in execution.
* **Vulnerabilities:** Security entry points (e.g., SQL injections, hardcoded credentials).
* **Code Smells:** Non-breaking bad practices that increase maintainability debt.


* **Quality Profile:** The **ruleset** applied during analysis (e.g., *"Do not allow unused imports"*). SonarQube provides a default called "Sonar way," but teams can customize rules per language.
* **Quality Gate:** The **pass/fail gatekeeper** for a pipeline run (e.g., *"Pass only if code coverage > 80% and zero critical security issues"*).
* **SonarScanner:** The CLI agent/runner that inspects code locally or inside CI/CD runners and uploads report artifacts to the SonarQube Server.

---

### Key Workflow Overview

```
[ Developer Push / PR ] 
       │
       ▼
[ GitHub Actions Pipeline ] 
       │
       ├─► 1. Checkout Code (fetch-depth: 0)
       ├─► 2. Run SonarScanner
       │        └─ Send report payload ──► [ SonarQube Server ]
       │                                         │
       └─◄ 3. Wait / Poll Quality Gate ◄─────────┴─ Evaluates Gate

```

---

### Core Integration Blueprint (GitHub Actions)

**1. Authentication Setup**

* **SonarQube Side:** Create a token (`User Account -> Security -> Generate Token`).
* **GitHub Side:** Save secrets in your repository under `Settings -> Secrets and Variables -> Actions`:
* `SONAR_TOKEN`: Token value generated from SonarQube.
* `SONAR_HOST_URL`: Server endpoint URL (e.g., `[https://sonarqube.example.com](https://sonarqube.example.com)`).



---

**2. `.github/workflows/sonarqube.yml**`

```yaml
name: SonarQube Analysis Workflow

on:
  push:
    branches: [ "main" ]
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  sonarqube:
    name: Code Quality Scan
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
        with:
          fetch-depth: 0  # Crucial: Disables shallow clones so SonarQube gets git blame & branch metrics

      - name: SonarQube Scan Action
        uses: SonarSource/sonarqube-scan-action@v2
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}
        with:
          args: >
            -Dsonar.projectKey=my-app-key
            -Dsonar.sources=.
            -Dsonar.exclusions=**/node_modules/**,**/*.spec.ts

      - name: Quality Gate Status Check
        uses: SonarSource/sonarqube-quality-gate-action@v1
        timeout-minutes: 5
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

```

### Language-Specific Integration Quick-Reference

| Stack | Scanner Integration Approach |
| --- | --- |
| **Java (Maven)** | Run Maven Plugin inline: `mvn clean verify sonar:sonar -Dsonar.projectKey=...` |
| **Java (Gradle)** | Apply `org.sonarqube` plugin in `build.gradle` & run `./gradlew sonar` |
| **Node.js / Python / Go** | Use `SonarSource/sonarqube-scan-action` action with a `sonar-project.properties` file |
| **.NET / C#** | Wrap build steps with `SonarScanner.MSBuild.exe begin` and `end` commands |

### High-Yield Interview / "Level-Up" Cheat Sheet

* **`fetch-depth: 0`:** Always include this in `actions/checkout`. Without full Git context, SonarQube cannot correctly identify who wrote broken lines of code or compute newly added code metrics.
* **Clean Code Strategy:** Focus quality gate rules primarily on **New Code** (e.g., PR diffs) rather than fixing entire legacy codebases all at once.
* **PR Decoration:** SonarQube communicates back with GitHub via webhooks/GitHub Apps to leave comments directly on Pull Requests showing whether Quality Gates passed or failed.
