# Trivy (Formally "tfsec")

**Trivy** (developed by Aqua Security) is an open-source, lightweight, and fast security scanner written in Go.

What makes Trivy unique compared to traditional scanners is its **all-in-one approach**: instead of relying on separate tools to scan your software packages, Docker images, infrastructure code, and secrets, Trivy performs all of these scans through a single binary.

---
### How Trivy identifies Issues without deploying?

**"Trivy identifies these issues using Static Analysis. It does not need to execute or deploy the code; instead, it reads your configuration files as plain text and compares them against a database of known security rules."**

If they ask you to elaborate, you can break it down into these three simple steps:

1. **Parsing:** Trivy reads your raw code (like your Terraform `.tf` files or Dockerfiles) without running them.
2. **Translation:** It converts that raw code into an internal, structured format(Abstract Syntax Tree or a JSON-like object) it can easily analyze.
3. **Rule Matching:** It cross-references that structure against its built-in vulnerability database (for CVEs) and its misconfiguration policies (like checking if an S3 bucket is missing an encryption flag). If it finds a match, it flags it in the report.

---

### How Trivy Works (Under the Hood)

Trivy operates in three distinct phases: **Ingestion**, **Analysis**, and **Matching**.

```
┌─────────────────┐       ┌────────────────────────┐       ┌──────────────────────┐
│  Target Input   │ ────> │ Local Parsing Engine   │ ────> │ Matching & Reporting │
│ (Image, FS, etc)│       │ Extract pkgs & lockfiles│       │ Cross-check Trivy DB │
└─────────────────┘       └────────────────────────┘       └──────────────────────┘

```

#### 1. Input Parsing & Inspection

When you point Trivy at a target (a local file system, a container image, or a Git repo):

* **For OS packages:** It reads the package manager metadata (e.g., `dpkg`, `rpm`, `apk`) to detect installed operating system libraries.
* **For Language Dependencies:** It searches for lockfiles (e.g., `package-lock.json`, `Cargo.lock`, `Pipfile.lock`, `go.sum`) to parse both direct and transitive dependencies.

#### 2. The Database Sync (`trivy-db`)

Trivy does not run a background server or database daemon. Instead, it uses a lightweight, local database cache.

* Before running a scan, Trivy automatically downloads an updated, highly optimized version of **Trivy DB** (rebuilt every few hours by Aqua Security).
* Trivy DB aggregates vulnerability feeds from multiple sources, including the National Vulnerability Database (NVD), GitHub Security Advisories (GHSA), and distribution-specific security trackers (Ubuntu, RedHat, Alpine, Debian).

#### 3. Matching & Severity Scoring

Trivy maps the exact package name and version parsed from your project against `trivy-db`. It outputs matching CVEs categorized by CVSS severity levels (*LOW*, *MEDIUM*, *HIGH*, *CRITICAL*) along with fixed version details.

---

### Important Features & Capabilities

* **Multi-Target Scanning:** Trivy can scan container images (`trivy image`), local directories/filesystems (`trivy fs`), remote Git repositories (`trivy repo`), virtual machine images, and live Kubernetes clusters (`trivy k8s`).
* **Comprehensive Vulnerability Coverage:** It detects vulnerabilities in both OS-level packages (Debian, Alpine, RHEL, etc.) and application-level language packages (npm, PyPI, Maven, Go, Cargo, Gem, etc.) in a single pass.
* **Secret & Misconfiguration Detection:** Beyond CVEs, Trivy checks for hardcoded secrets (API keys, passwords) and scans Infrastructure as Code (IaC) files (Terraform, Dockerfiles, Kubernetes manifests) for security risks.
* **SBOM Generation & Audit:** Supports exporting and reading Software Bill of Materials in industry-standard formats such as **CycloneDX** and **SPDX**.

---

### Key Operational Strengths

* **Zero-Dependency Installation:** Distributed as a single executable static binary. You do not need Docker, Java, or a running database engine to perform local scans.
* **High CI/CD Compatibility:** Extremely fast execution speeds make it a popular choice for GitHub Actions, GitLab CI, and Jenkins pipelines to gate builds.
* **No Server Required:** Runs fully client-side out of the box, making it easy to run offline or in air-gapped environments (by pre-downloading the database).

### Basic Commands to Get Started

| Task | Command |
| --- | --- |
| **Scan a Docker Image** | `trivy image python:3.10-alpine` |
| **Scan Local Directory** | `trivy fs /path/to/project` |
| **Scan a Git Repo** | `trivy repo [https://github.com/user/repo](https://github.com/user/repo)` |
| **Generate an SBOM** | `trivy image --format cyclonedx nginx:latest` |
| **Filter Unfixed CVEs** | `trivy image --ignore-unfixed alpine:3.18` |

## Trivy Realtime example with Terraform & Githubactions integration:

### 1. Local Workflow: Scanning Terraform with Trivy

Before committing code, you can use Trivy locally to scan your HashiCorp Configuration Language (HCL) files for infrastructure misconfigurations, such as unencrypted S3 buckets, overly permissive security groups, or hardcoded secrets.

To scan a directory containing Terraform files, use the `config` command:

```bash
# Navigate to your Terraform directory
cd my-terraform-project/

# Run Trivy IaC (Infrastructure as Code) scan
trivy config .

```

To filter for specific severity levels and force a non-zero exit code (which is useful for testing CI/CD logic locally):

```bash
trivy config --severity HIGH,CRITICAL --exit-code 1 .

```

### 2. GitHub Actions CI/CD Integration Workflow

To automate this check, you can integrate [Trivy](https://github.com/SSSPRABHUDINESH/DevOps_Notes/blob/main/Github-Actions/20.3%20Trivy%20-%20Scanning%20tool.md?utm_source=gemini) into your GitHub Actions pipeline. The pipeline will intercept any pull request or commit, scan the Terraform code, and block the deployment if critical misconfigurations are found.

Create a file in your repository at `.github/workflows/terraform-trivy.yml` and add the following configuration:

```yaml
name: Terraform Security Scan

# Trigger the workflow on pushes to main and any pull requests
on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]

jobs:
  trivy-iac-scan:
    name: Trivy IaC Scanner
    runs-on: ubuntu-latest
    
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      # Run Trivy to scan the Terraform configuration
      - name: Run Trivy vulnerability scanner in IaC mode
        uses: aquasecurity/trivy-action@master
        with:
          scan-type: 'config'
          scan-ref: '.'          # Scans the root directory containing Terraform files
          hide-progress: false
          format: 'table'
          exit-code: '1'         # Fails the pipeline if vulnerabilities are found
          ignore-unfixed: true
          severity: 'CRITICAL,HIGH' # Only fail on HIGH or CRITICAL issues

  # This job only runs if the Trivy scan passes
  terraform-deploy:
    name: Terraform Plan & Apply
    needs: trivy-iac-scan
    runs-on: ubuntu-latest
    
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v2
        with:
          terraform_version: 1.5.0

      - name: Terraform Init
        run: terraform init

      - name: Terraform Plan
        run: terraform plan

      # Only apply on push to the main branch, not on PRs
      - name: Terraform Apply
        if: github.event_name == 'push'
        run: terraform apply -auto-approve

```

### 3. How the CI/CD Pipeline Behaves

* **Code Commit / Pull Request:** When a developer pushes Terraform changes, the `trivy-iac-scan` job starts immediately.
* **The Scan:** The official `aquasecurity/trivy-action` pulls the latest Trivy vulnerability database and parses your `.tf` files.
* **Quality Gate Enforcement:**
* If Trivy finds any misconfigurations marked as `HIGH` or `CRITICAL` (e.g., an AWS RDS instance missing encryption), it exits with code `1`. The pipeline **fails**, the Pull Request is blocked, and the `terraform-deploy` job never runs.
* If Trivy finds only `LOW` or `MEDIUM` issues (or no issues at all), the pipeline **passes**.


* **Deployment:** Once the scan passes, the pipeline proceeds to the `terraform-deploy` job to initialize and apply your infrastructure safely.

## Prequisites:

### Should I need to install Trivy on Runner?

**No, you do not need to manually install Trivy on the runner.**

When you use `uses: aquasecurity/trivy-action@master`, the GitHub Action handles downloading the latest Trivy binary and running it automatically in the background. You do not need to add any `apt-get install` or download scripts to your workflow.

### Prerequisites to Run the Complete Workflow

To successfully run the CI/CD workflow (Trivy scan followed by Terraform apply), you need the following in place:

1. **Terraform Configuration Files:** Your repository must contain valid Terraform `.tf` files in the directory you are scanning and deploying.
2. **Cloud Provider Credentials (Secrets):** Because the second job runs `terraform plan` and `terraform apply`, Terraform needs permission to talk to your cloud provider (AWS, GCP, Azure, etc.). You must store these as GitHub Secrets and expose them to the workflow.
* *Example for AWS:* You would need to add `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` to your repository secrets and inject them into the deployment job.


3. **Configured Remote State:** Since GitHub Actions runners are ephemeral (they are destroyed after the pipeline finishes), you cannot store your `terraform.tfstate` file locally on the runner. You must configure a remote backend in your Terraform code (e.g., an AWS S3 bucket, GCP Cloud Storage, or Terraform Cloud).
4. **Actions Permissions:** Ensure GitHub Actions is allowed to read your repository code. The default permissions provided to the `actions/checkout` step are usually sufficient for this.

## Realtime Example:
This video provides a practical tutorial on using **Trivy**, an open-source security tool, to scan *Docker* images for vulnerabilities and remediate them.

### **Phase 1: Installation and Scanning**
* **Goal:** Identify security weaknesses in an existing *Docker* image named `sample-app2`.
* **Process:** 
    * Install *Trivy* by adding the repository and updating the package manager .
    * Scan the image using the `trivy` command (`trivy image sample-app2` and export the results to a text file for better readability.
* **Outcome:** The initial scan revealed numerous vulnerabilities, particularly within the *OpenJDK* package.

### **Phase 2: Vulnerability Remediation**
* **Root Cause Analysis:** The creator identified that the `Dockerfile` was using an outdated, unmaintained official *OpenJDK 8 Alpine* base image.
* **Fixing the issue:**
    * Instead of relying on the old base, the creator built a custom image using the **latest** *Alpine* base image.
    * The new *Dockerfile* updates the base image and installs *OpenJDK 8* manually.
    * The new image, `sample-app4`, was built and successfully scanned.
* **Conclusion:** By updating the base image, most of the previously detected vulnerabilities were resolved.
