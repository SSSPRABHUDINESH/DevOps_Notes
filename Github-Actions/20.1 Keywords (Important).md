## Keywords

The key keywords in GitHub Actions, organized by their scope and purpose:

| Keyword | Level / Scope | Purpose & Description | Example Usage |
| --- | --- | --- | --- |
| **`name`** | Workflow / Job / Step | Label displayed in the GitHub UI for the workflow, job, or individual step. | `name: CI Build Pipeline` |
| **`on`** | Workflow | **(Required)** Defines the event(s) that trigger the workflow to run (e.g., `push`, `pull_request`, `schedule`). | `on: [push, pull_request]` |
| **`jobs`** | Workflow | **(Required)** Groups all the individual jobs that will execute during the workflow run. | `jobs:` |
| **`runs-on`** | Job | **(Required)** Specifies the type of runner machine (e.g., `ubuntu-latest`, `windows-latest`, `self-hosted`). | `runs-on: ubuntu-latest` |
| **`steps`** | Job | **(Required)** An ordered sequence of tasks (commands or actions) executed inside the job. | `steps:` |
| **`uses`** | Step | Invokes a pre-built reusable **Action** from GitHub Marketplace or another repository/local path. | `uses: actions/checkout@v4` |
| **`run`** | Step | Executes shell commands or inline scripts directly on the runner machine. | `run: npm install && npm test` |
| **`with`** | Step / Job | Passes input parameters/arguments to an Action (used with `uses`). | `with: node-version: '20'` |
| **`env`** | Workflow / Job / Step | Declares environment variables accessible within that specific block's execution scope. | `env: NODE_ENV: production` |
| **`needs`** | Job | Sets job dependencies to force jobs to run sequentially rather than in parallel. | `needs: build` |
| **`if`** | Job / Step | Sets conditional execution rules (runs the job/step only if the condition evaluates to `true`). | `if: github.ref == 'refs/heads/main'` |
| **`strategy`** | Job | Configures execution strategies like build matrices or max parallel instances. | `strategy: matrix: os: [ubuntu-latest, macos-latest]` |
| **`matrix`** | Job (`strategy`) | Defines combinations of variables to run multiple variations of the same job simultaneously. | `matrix: node: [18, 20]` |
| **`defaults`** | Workflow / Job | Sets default settings (like default `working-directory` or default `shell`) for steps. | `defaults: run: shell: bash` |
| **`concurrency`** | Workflow / Job | Ensures that only a single job or workflow using the same concurrency group runs at a time. | `concurrency: group: prod-deploy` |
| **`permissions`** | Workflow / Job | Modifies the `GITHUB_TOKEN` permissions granted to the workflow/job. | `permissions: contents: read` |
| **`timeout-minutes`** | Job / Step | Sets the maximum runtime allowed for a job or step before GitHub automatically cancels it. | `timeout-minutes: 30` |
| **`continue-on-error`** | Job / Step | Allows the workflow to keep running even if this specific job or step fails. | `continue-on-error: true` |
| **`outputs`** | Job / Step | Declares output variables generated by a job or step so they can be consumed by later steps/jobs. | `outputs: artifact-id: ${{ steps.build.outputs.id }}` |
| **`container`** | Job | Executes the job steps inside a specific Docker container instead of directly on the runner host. | `container: image: node:20-alpine` |
| **`services`** | Job | Spins up sidecar container services (e.g., Redis, Postgres) for integration testing during the job. | `services: postgres: image: postgres:15` |
| **`id-token: write`** | Workflow | Grants the workflow runner permission to request a dynamic, short-lived OpenID Connect (OIDC) JSON Web Token (JWT) from GitHub’s identity provider. This token is what lets your workflow authenticate securely with GCP or Vault without static API keys. | `permissions:  id-token: write  contents: read` |
| **`contents: read`** | Workflow | Explicitly re-enables repository read access. As noted in the document, the moment you explicitly define any custom permission (like `id-token: write`), GitHub automatically revokes all other default token permissions. Without adding `contents: read`, action steps like `actions/checkout@v4` will fail because the runner loses the ability to clone your repository's code. | `permissions:  id-token: write  contents: read` |
| **`environment`** | Job | Targets a specific deployment environment (e.g., `production`), enabling protection rules and secrets. | `environment: production` |
