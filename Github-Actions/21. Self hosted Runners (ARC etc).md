## 1. GitHub-Hosted vs. Self-Hosted Runners

### Deep Comparison

| Capability / Metric | GitHub-Hosted Runners | Self-Hosted Runners |
| --- | --- | --- |
| **Infrastructure Management** | Fully managed by GitHub (SaaS) | Customer managed (Cloud, On-Prem, K8s) |
| **Network & Firewall Access** | External IPs; requires NAT/VPN for private resources | Native access to private VPCs, databases, and internal APIs |
| **Security Lifecycle** | Clean VM isolated per job (Zero persistence) | Can be persistent (risk of pollution) or ephemeral |
| **Hardware Flexibility** | Standard CPU/RAM tiers (Standard & Larger Runners) | Custom hardware support (GPUs, ARM, High RAM) |
| **Cost Model** | Pay-per-minute execution fee | Fixed infrastructure cost (Compute + Memory + Storage) |
| **Egress Costs** | Free out-of-band artifact transfers within GitHub | Standard Cloud Provider egress rates apply |

### Key Enterprise Trade-offs

* **GitHub-Hosted:** Eliminates operational overhead and patched maintenance. However, it requires exposing internal endpoints or maintaining dynamic IP allowlists (or using GitHub Private Networking).
* **Self-Hosted:** Provides speed, internal network connectivity, and specialized hardware. However, it introduces operational overhead, security patching duties, and potential runner contamination if persistent runners are improperly configured.

### Real-World Production Use Cases

* **GitHub-Hosted:** Microservice unit testing, linting, public package publishing, and standard SaaS deployments.
* **Self-Hosted:** Database schema migrations inside private subnets, ML/AI model training requiring CUDA GPUs, legacy builds needing specific OS kernels, and air-gapped environment builds.

# Comprehensive Guide: Self-Hosted GitHub Actions Runners on Virtual Machines (VMs)

---

## 1. Architectural Fundamentals & Networking Model

### What is a VM Self-Hosted Runner?

A **Self-Hosted Runner on a VM** is an infrastructure instance (such as an AWS EC2 instance, GCP Compute Engine VM, Azure VM, or on-premises server) running the official **GitHub Actions Runner Application**.

Unlike GitHub-hosted runners managed fully by GitHub, self-hosted runners execute workflow jobs on your own computing resources, giving you direct control over custom hardware, private network access, tools, and persistent caching.

### The Connection Model: Inbound vs. Outbound Architecture

A common misconception is that a self-hosted runner acts as an HTTP server waiting for GitHub to send commands. **It is NOT a web server.**

```text
❌ WRONG INBOUND MODEL (Web Server):
GitHub Cloud  ──►  [Public IP / Open Port 443]  ──►  Virtual Machine (Requires Firewall Holes)

✅ ACTUAL OUTBOUND MODEL (Long-Polling):
Virtual Machine  ──►  [Outbound HTTPS / Port 443]  ──►  GitHub API (Secure & VPC-Friendly)

```

#### Why Outbound Long-Polling Matters

1. **Zero Inbound Ports Required:** Your VM does not need a public IP address, open inbound security groups, or an ingress web server (like Nginx).
2. **VPC-Friendly:** The runner connects via outbound HTTPS over standard Port 443 (`[https://pipelines.actions.githubusercontent.com](https://pipelines.actions.githubusercontent.com)`).
3. **HTTP Long-Polling Protocol:** The VM opens a secure connection and asks: *"Is there a job in my queue?"* GitHub holds the request open for up to **50 seconds**. If a job arrives, GitHub pushes the payload immediately down that connection. If the timeout expires with no jobs, the VM instantly initiates a new request.

## 3. Step-by-Step Provisioning & Configuration Guide

### Prerequisites

* A Virtual Machine (Ubuntu, RHEL, Windows, or macOS) with outbound internet access.
* A GitHub Personal Access Token (PAT) or Organization admin permissions to generate a **Registration Token**.

1. **Obtain a Registration Token from GitHub:** Admin Panel.
Navigate to your **GitHub Repository or Organization Settings** $\rightarrow$ **Actions** $\rightarrow$ **Runners** $\rightarrow$ **New self-hosted runner**. Copy the temporary registration token generated by GitHub.


2. **Download and Extract the Runner Package:** VM Terminal.
SSH into your virtual machine and pull down the official release package.

```bash

mkdir actions-runner && cd actions-runner

# Download official Linux x64 runner release

tar xzf ./actions-runner-linux-x64-2.311.0.tar.gz

```


3. **Register the Runner with the --ephemeral Flag:** Core Configuration.
Execute `./config.sh` to pair the VM with your repository. Adding the **`--ephemeral`** flag guarantees the runner processes exactly **one job** and immediately unregisters itself.

```bash
./config.sh \
  --url https://github.com/Your-Org/Your-Repo \
  --token AXXYYZZ12345EXAMPLE \
  --name "aws-ubuntu-runner-01" \
  --labels "ubuntu-latest,custom-aws" \
  --ephemeral \
  --unattended

```


4. **Start the Runner Loop or System Service:** Execution Phase.
Launch the process directly for testing, or install it as a background OS service for persistence.

```bash
# Option A: Interactive foreground execution (for testing)
./run.sh

# Option B: Background system service (for production persistence)
sudo ./svc.sh install
sudo ./svc.sh start

```

## 4. Persistent vs. Ephemeral Execution Modes

Self-hosted runners can operate under two distinct execution strategies depending on security requirements and resource management.

| Feature | Persistent Runner (Default) | Ephemeral Runner (`--ephemeral`) |
| --- | --- | --- |
| **Lifecycle** | Stays alive indefinitely across multiple sequential jobs. | Processes **one job** and immediately unregisters and terminates. |
| **State Cleanliness** | Leftover workspace files, cache, or ambient processes carry over to next job. | Environment is destroyed after execution; zero state contamination. |
| **Security Risk** | Higher. Secrets or credentials written to disk by Job A might be exposed to Job B. | High. Guarantees fresh state for every pipeline execution. |
| **Target Infrastructure** | Static, long-running Virtual Machines. | Auto-scaling VM groups (AWS ASG, GCP MIGs) or Kubernetes (ARC). |
| **Configuration** | `./config.sh` | `./config.sh --ephemeral` |

## 5. End-to-End Workflow Execution & Auto-Scaling Lifecycle

```text
 1. Trigger           2. Pickup           3. Execution         4. Deregistration      5. Destruction & Re-spin
┌──────────────┐     ┌─────────────┐     ┌──────────────┐     ┌────────────────┐     ┌──────────────────────┐
│ Dev pushes   │────►│ Runner pulls│────►│ Executes     │────►│ Unregisters    │────►│ Auto-Scaling Group   │
│ PR tagged    │     │ job via     │     │ workflow     │     │ from GitHub    │     │ terminates old VM    │
│ self-hosted  │     │ Long-Poll   │     │ steps        │     │ and exits      │     │ & provisions new VM  │
└──────────────┘     └─────────────┘     └──────────────┘     └────────────────┘     └──────────────────────┘

```

1. **Trigger:** A workflow run requests `runs-on: self-hosted`.
2. **Matching & Pickup:** GitHub assigns the job to the registered idle runner `aws-ubuntu-runner-01`.
3. **Execution:** The VM executes the step commands (`actions/checkout`, shell scripts, test suites).
4. **Auto-Deregistration:** Because `--ephemeral` was set during configuration, the `./run.sh` process unregisters itself from GitHub the moment the job finishes.
5. **Infrastructure Cleanup:** An external auto-scaler (e.g., AWS Auto Scaling Group lifecycle hook or custom daemon) detects that `./run.sh` exited, **terminates the VM instance**, and launches a clean replacement VM to await the next job.

## 3. Foreground Execution vs. OS Background Service (`./run.sh` vs. `./svc.sh`)

When running the application on a VM, you can execute it interactively via `./run.sh` or register it as an OS background daemon using `./svc.sh`.

### Why `./svc.sh` is Necessary for Production

Executing `./run.sh` directly attaches the runner process to your active SSH/terminal session. Closing your terminal sends a termination signal (`SIGINT`/`SIGHUP`), killing the runner immediately. `./svc.sh` packages the runner into an OS system service (`systemd` on Linux, `launchd` on macOS, Windows Services).

| Capability | Foreground (`./run.sh`) | Background Service (`sudo ./svc.sh`) |
| --- | --- | --- |
| **Execution Mode** | Interactive foreground process | Background OS Daemon (`systemd`) |
| **Close Terminal / SSH** | ❌ Process terminates immediately | ✅ Keeps running continuously |
| **System Reboot** | ❌ Remains offline | ✅ Auto-starts on OS boot |
| **Process Crash** | ❌ Stays dead | ✅ Auto-restarted by OS init system |
| **Best Used For** | Initial testing & debugging | Permanent, static persistent runners |

### Key `./svc.sh` Management Commands

```bash
# 1. Install system daemon entry
sudo ./svc.sh install

# 2. Start background daemon
sudo ./svc.sh start

# 3. Check service health status
sudo ./svc.sh status

# 4. Stop service execution
sudo ./svc.sh stop

# 5. Remove daemon entry from host OS
sudo ./svc.sh uninstall

```

> **OS-Level Verification:** You can also verify daemon state directly via `systemctl status actions.runner.*` or check auto-start enablement with `systemctl is-enabled actions.runner.*`.

## 4. Operational Architectural Trap: `--ephemeral` + `svc.sh` Conflict

Combining the `--ephemeral` flag with the system daemon (`./svc.sh`) creates a severe operational failure:

```text
Step 1: Job completes ──► Runner unregisters from GitHub & deletes local credentials
Step 2: Process exits ──► systemd detects exit & automatically restarts binary
Step 3: CrashLoop     ──► Binary fails launch (missing credentials) ──► Runner Goes Offline

```

* **Rule of Thumb:**
* **Use `./svc.sh` ONLY for static persistent runners.** The VM stays alive, picks up jobs sequentially, and keeps local state/caches across builds.
* **Use `--ephemeral` ONLY with automated disposable infrastructure** (AWS ASG, GCP MIGs, or Kubernetes ARC) where an external controller destroys the host VM/Pod upon process exit and spins up a fresh instance.

## 6. Execution Model Summary: Persistent vs. Ephemeral

```text
PERSISTENT MODEL (Static VM + svc.sh):
  [Job 1 Run] ──► [Clean workspace/caches remain] ──► [Job 2 Run] ──► [VM stays online forever]

EPHEMERAL MODEL (Auto-Scaling VM + --ephemeral):
  [Job 1 Run] ──► [Runner unregisters & exits] ──► [Auto-scaler terminates VM] ──► [Clean VM launched]

```

| Dimension | Persistent Runner (`svc.sh`) | Ephemeral Runner (`--ephemeral`) |
| --- | --- | --- |
| **Daemon Management** | OS Systemd Service via `./svc.sh` | Interactive process loop via `./run.sh` |
| **Job Capacity** | Multiple sequential jobs | Exactly **one** job |
| **Post-Job Action** | Returns to `Idle` listening state | Unregisters and shuts down process |
| **State Cleanliness** | Caches & files persist between builds | Environment destroyed; zero state leakage |
| **Target Setup** | Long-running static Virtual Machines | Auto-Scaling Groups (AWS ASG/GCP MIG) or ARC |

## 2. Ephemeral Runners

An **Ephemeral Runner** is a single-use worker instance. It registers with GitHub, accepts **exactly one job**, executes it, and is immediately destroyed upon job completion.

### The Security & Reliability Hazard of Persistent Runners

```
[ Persistent Runner Instance ]
Job 1: Installs custom tool / Leaves credentials in /tmp / Modifies system config
       │
       ▼
Job 2: Inherits contaminated state from Job 1 ──► Risk of credential theft or false passes

```

### The Ephemeral Solution Architecture

```
[ Trigger Event ] ──► [ Provision Clean Pod/VM ] ──► [ Process Single Job ] ──► [ Destroy Worker ]

```

### Key Advantages

1. **Zero State Leakage:** Prevents build artifacts, environment variables, or temporary tokens from persisting into subsequent builds.
2. **Deterministic Builds:** Guarantees that every build runs against a clean environment, eliminating "works on my machine" inconsistencies.
3. **Automated Credential Flush:** Short-lived tokens stored in memory or `/tmp` vanish when the instance terminates.

### Implementation Pattern (`--ephemeral` Flag)

When registering a runner manually via the CLI, the `--ephemeral` flag enforces auto-deregistration after a single job execution:

```bash
./config.sh --url https://github.com/Your-Org/Your-Repo \
  --token <REGISTRATION_TOKEN> \
  --name "ephemeral-runner-01" \
  --ephemeral \
  --unattended

```

## 1. Architectural Overview & Fundamentals

### What is Actions Runner Controller (ARC)?

**Actions Runner Controller (ARC)** is a Kubernetes operator created and maintained officially by GitHub. It automates the provisioning, scaling, and lifecycle management of self-hosted GitHub Actions runners inside a Kubernetes cluster (such as Google Kubernetes Engine - GKE).

Instead of managing static Virtual Machines (VMs) or manually running registration scripts, ARC extends the native Kubernetes API using **Custom Resource Definitions (CRDs)** to manage runner pools dynamically based on workflow demand.

## 2. Component Separation: Manager vs. Workers

ARC strictly divides responsibilities between two separate layers inside the cluster to ensure security, high availability, and isolation.

| Dimension | Manager (Controller) Plane | Worker (Execution) Plane |
| --- | --- | --- |
| **Namespace** | `arc-systems` | `arc-runners` (or custom names per team) |
| **Helm Chart** | `gha-runner-scale-set-controller` | `gha-runner-scale-set` |
| **Primary Role** | Runs the Go-based Kubernetes Operator. Manages CRDs and cluster reconciliation. | Listens for jobs and executes CI/CD workflow code. |
| **Lifecycle** | Long-running, persistent deployments (1-2 controller pods). | Ephemeral. Spun up on-demand per job and destroyed immediately on completion. |
| **Access Rights** | Requires ClusterRole permissions to create/delete pods and manage CRDs. | Restricted permissions matching workload requirements. |

## 3. Communication & Networking Architecture

### How Outbound Connection Works

Self-hosted runners on Kubernetes **do not expose any inbound ports** and do not require public IP addresses or ingress controllers.

1. **Outbound Initiation:** The `Auto-Scaling Listener Pod` inside `arc-runners` opens an outbound HTTPS connection (Port 443 over WebSockets / HTTP Long-Polling) to `[https://pipelines.actions.githubusercontent.com](https://pipelines.actions.githubusercontent.com)`.
2. **Firewall Compatibility:** As long as your GKE cluster has basic outbound internet connectivity (direct internet access or via **GCP Cloud NAT** for private clusters), ARC connects without inbound firewall configuration.
3. **Polling Loop:** The Listener pod holds an open HTTP connection with GitHub. When a job matching the runner scale set triggers, GitHub immediately pushes the job payload down that existing connection.

| Execution Mechanism | Manual VM Runner Setup | ARC on Kubernetes |
| --- | --- | --- |
| **Registration** | Manual execution of `./config.sh --token <TOKEN>` | Automated by ARC via Kubernetes secrets and GitHub API. |

## 5. Step-by-Step Production Deployment Guide

### Prerequisites

* A running **GKE Cluster** with `kubectl` configured locally (`gcloud container clusters get-credentials`).
* **Helm 3.x** installed.
* A GitHub **Personal Access Token (PAT)** (or GitHub App) with `repo` / `admin:org` permissions.

---

1. **Install the ARC Controller Manager:** Prerequisite - Run once per cluster.
Deploy the core operator into a dedicated, isolated namespace named `arc-systems`.

```bash
# 1. Add the GitHub Actions Runner Controller Helm repository
helm repo add actions-marketplace https://github.io
helm repo update

# 2. Install the controller chart
helm upgrade --install arc \
    --namespace arc-systems \
    --create-namespace \
    oci://ghcr.io/actions/actions-runner-controller-charts/gha-runner-scale-set-controller

```


2. **Configure Authentication Secret:** Security step.

**Step 1:** Create Personal Access Token 

To create a **GitHub Personal Access Token (PAT)** for authentication (such as registering runners or configuring Actions Runner Controller), generate one directly from your GitHub account settings.

1. **Navigate to Developer Settings:**
Log into your GitHub account, click your profile picture in the top-right corner, select **Settings**, and scroll down to click **Developer settings** in the left sidebar.


2. **Select Token Type:**
Under **Personal access tokens**, choose either **Tokens (classic)** or **Fine-grained tokens** depending on your organization's security policy. Click **Generate new token**.


3. **Configure Permissions & Generate:**
Give your token a descriptive name (Note), set an expiration date, and select the required scopes (for ARC/Runners, typically **`repo`**, **`admin:org`**, or **`manage_runners`**). Click **Generate token**.


4. **Copy and Save Token:**
Copy the generated token string immediately. GitHub will only show this value to you once.

**Step 2:** Create kubernetes secret

Create a Kubernetes secret containing your GitHub authorization token inside the worker namespace.

```bash
# 1. Create the dedicated worker namespace
kubectl create namespace arc-runners

# 2. Store the token as a Kubernetes Secret
kubectl create secret generic github-token \
    --namespace arc-runners \
    --from-literal=github_token="YOUR_GITHUB_PERSONAL_ACCESS_TOKEN"

```


3. **Deploy the Runner Scale Set:** Execution pool setup.
Deploy the worker listener chart. This automatically registers the runner pool within your GitHub organization or repository settings.

```bash
helm upgrade --install gke-runner-set \
    --namespace arc-runners \
    oci://ghcr.io/actions/actions-runner-controller-charts/gha-runner-scale-set \
    --set githubConfigUrl="https://github.com/Your-Org/Your-Repo" \
    --set githubConfigSecret=github-token

```

## 6. How to Direct Workflow Jobs to GKE Runners

Once installed, ARC automatically manages registration in the GitHub UI. You **do not** need to click "New self-hosted runner" in GitHub.

To route your GitHub Actions pipelines to your GKE runner cluster, set the `runs-on` property in your workflow YAML file to match your **Helm release name** (`gke-runner-set` in our example).

### Sample `.github/workflows/ci.yml`

```yaml
name: GKE CI Pipeline

on:
  push:
    branches: [ "main" ]

jobs:
  build-and-test:
    # Must match the Helm installation name of your Runner Scale Set
    runs-on: gke-runner-set

    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Verify Environment
        run: |
          echo "Executing on GKE Ephemeral Runner"
          uname -a
          kubectl version --client || true

```

## 1. Container vs. VM Architectural Model

Running GitHub Actions runners inside Docker containers shifts runner management from heavy virtual machines to lightweight, fast-starting container workloads.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                            Host Machine (VM or Bare Metal)                  │
│                                                                             │
│  ┌───────────────────────────┐                 ┌─────────────────────────┐  │
│  │ Docker Engine / Daemon    │                 │ Host OS Resources       │  │
│  └─────────────┬─────────────┘                 └─────────────────────────┘  │
│                │                                                            │
│                ▼                                                            │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ Container Context (Docker Runner Container)                           │  │
│  │                                                                       │  │
│  │  ┌─────────────────────────────────────────────────────────────────┐  │  │
│  │  │ Entrypoint Script (entrypoint.sh)                               │  │  │
│  │  │ 1. Generates ephemeral runner token via GitHub API              │  │  │
│  │  │ 2. Executes ./config.sh --ephemeral                             │  │  │
│  │  │ 3. Execs ./run.sh                                               │  │  │
│  │  └────────────────────────────────┬────────────────────────────────┘  │  │
│  │                                   │                                   │  │
│  │                                   ▼                                   │  │
│  │  ┌─────────────────────────────────────────────────────────────────┐  │  │
│  │  │ Runner.Listener Process                                         │  │  │
│  │  │ - Outbound HTTPS Long-Polling (Port 443) to GitHub API          │  │  │
│  │  └─────────────────────────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘

```

### Core Execution Differences

* **Network Model:** Outbound long-polling over Port 443 remains identical to VMs. Zero inbound firewall rules or ingress endpoints needed.
* **Process Lifecycle:** Instead of systemd services (`./svc.sh`), Docker container lifecycles are tied directly to PID 1 (`entrypoint.sh` executing `./run.sh`).
* **Isolation:** Jobs run inside isolated container environments without altering host OS dependencies.

Here is a complete comparison between the **Manual (VM-style)** approach and the **Automated (`entrypoint.sh`)** approach for running GitHub self-hosted runners in Docker. You can directly copy this into your notes.

---

### Method 1: The Manual Approach (Interactive / Exec)

This method mirrors how you set up a standard Virtual Machine or bare-metal server. You start the container, attach to its shell, register it with GitHub manually, and leave it running.

**1. Create a minimal `Dockerfile` (No entrypoint needed):**

```dockerfile
FROM ubuntu:22.04

# Install basic dependencies required by the runner
RUN apt-get update && apt-get install -y \
    curl tar jq git build-essential libssl-dev libffi-dev python3-dev \
    && rm -rf /var/lib/apt-get/lists/*

# Create a non-root user (GitHub runner cannot run as root)
RUN useradd -m runner
USER runner
WORKDIR /home/runner

# Download and extract the runner package
ARG RUNNER_VERSION="2.311.0"
RUN curl -o actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz -L \
    https://github.com/actions/runner/releases/download/v${RUNNER_VERSION}/actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz \
    && tar xzf ./actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz \
    && rm actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz

# Install runner OS dependencies
USER root
RUN ./bin/installdependencies.sh
USER runner

# Keep container running indefinitely so you can exec into it
CMD ["tail", "-f", "/dev/null"]

```

**2. Build and run the container:**

```bash
docker build -t manual-runner .
docker run -d --name my-runner manual-runner

```

**3. Manually register and start the runner:**

```bash
# Get inside the running container
docker exec -it my-runner bash

# Run the config script using the token generated from GitHub UI
./config.sh --url https://github.com/Your-Org/Your-Repo --token YOUR_REGISTRATION_TOKEN

# Start listening for workflow jobs
./run.sh

```

## Method 2: The Automated Approach (Using `entrypoint.sh`)
---
### 2. Dynamic Registration & Dockerfile Architecture

Because Docker containers are disposable by design, static configuration (`./config.sh`) baked into images is an anti-pattern. Registration tokens must be fetched dynamically at runtime via the GitHub API using a Personal Access Token (PAT) or GitHub App credentials.

### Production Dockerfile (`Dockerfile`)

```dockerfile
FROM ubuntu:22.04

# Prevent interactive prompts during package installation
ENV DEBIAN_FRONTEND=noninteractive

# Install core runner dependencies and Docker CLI
RUN apt-get update && apt-get install -y \
    curl \
    jq \
    build-essential \
    libssl-dev \
    libffi-dev \
    python3 \
    git \
    docker.io \
    && rm -rf /var/lib/apt/lists/*

# Set up non-root runner user
RUN useradd -m runner && usermod -aG docker runner
WORKDIR /home/runner

# Download and extract the GitHub Actions runner binary
ARG RUNNER_VERSION="2.311.0"
RUN curl -o actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz -L \
    https://github.com/actions/runner/releases/download/v2.${RUNNER_VERSION}/actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz \
    && tar xzf ./actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz \
    && rm actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz

# Install runner OS dependencies script
RUN ./bin/installdependencies.sh

COPY entrypoint.sh /home/runner/entrypoint.sh
RUN chmod +x /home/runner/entrypoint.sh

USER runner
ENTRYPOINT ["/home/runner/entrypoint.sh"]

```

### Container Startup Script (`entrypoint.sh`)

```bash
#!/bin/bash
set -e

# Require environment variables
if [ -z "$GITHUB_ORGANIZATION" ] || [ -z "$GITHUB_PAT" ]; then
  echo "Error: GITHUB_ORGANIZATION and GITHUB_PAT must be set."
  exit 1
fi

# Fetch short-lived registration token dynamically from GitHub API
REGISTRATION_TOKEN=$(curl -s -X POST \
  -H "Authorization: token ${GITHUB_PAT}" \
  -H "Accept: application/vnd.github.v3+json" \
  "https://api.github.com/orgs/${GITHUB_ORGANIZATION}/actions/runners/registration-token" | jq -r .token)

# Register container runner with ephemeral flag
./config.sh \
  --url "https://github.com/${GITHUB_ORGANIZATION}" \
  --token "${REGISTRATION_TOKEN}" \
  --name "docker-runner-$(hostname)" \
  --work "_work" \
  --labels "docker-runner,ubuntu-latest" \
  --ephemeral \
  --unattended

# Cleanup function to gracefully unregister on SIGTERM/SIGINT
cleanup() {
  echo "Caught signal, unregistering runner..."
  REMOVE_TOKEN=$(curl -s -X POST \
    -H "Authorization: token ${GITHUB_PAT}" \
    -H "Accept: application/vnd.github.v3+json" \
    "https://api.github.com/orgs/${GITHUB_ORGANIZATION}/actions/runners/remove-token" | jq -r .token)
  ./config.sh remove --token "${REMOVE_TOKEN}"
}

trap 'cleanup' SIGINT SIGTERM

# Hand off execution to run script
./run.sh &
RUN_PID=$!
wait $RUN_PID

```

### Comparison Summary

| Feature | Manual (`exec -it`) | Automated (`entrypoint.sh`) |
| --- | --- | --- |
| **Setup Effort** | Manual command entry per container. | Fully automated on `docker run`. |
| **Use Case** | Debugging, testing, local development. | Production, auto-scaling, Kubernetes. |
| **Deregistration** | Requires running `./config.sh remove` manually. | Handled automatically via `trap` signal handlers. |
| **Container Lifecycle** | Keeps container idle via `tail -f`. | Tied directly to the execution of `./run.sh`. |

## 3. Handling Docker-in-Docker (DinD) vs. Docker Socket Mounting

When workflow steps run `docker build` or `docker run`, the containerized runner needs access to a Docker daemon.

```text
APPROACH A: Docker Socket Mount (DooD - Docker Out-of-Docker)
Containerized Runner  ──────/var/run/docker.sock──────►  Host Docker Daemon (Fast, Shared Cache)

APPROACH B: Docker-in-Docker (DinD)
Containerized Runner  ──►  [Isolated Inner Docker Daemon] (Privileged Mode, Secure Isolation)

```

| Dimension | Docker Socket Mounting (DooD) | Docker-in-Docker (DinD) |
| --- | --- | --- |
| **Configuration** | Mount host socket: `-v /var/run/docker.sock:/var/run/docker.sock` | Run container in privileged mode: `--privileged` |
| **Daemon Context** | Reuses the **Host** Docker daemon. | Runs an isolated Docker daemon **inside** the container. |
| **Image Caching** | High efficiency. Build images persist on host cache across runs. | Zero cache reuse by default; images discarded when container exits. |
| **Security Risk** | **High.** Container access to host socket allows root-equivalent host takeover. | **Moderate.** Requires `--privileged` flag, bypassing container safety boundaries. |
| **Best Used For** | Trusted internal pipelines needing fast build times. | Untrusted code execution or multi-tenant pipeline platforms. |

---

## 4. Execution Strategies: Persistent vs. Ephemeral Containers

| Feature | Persistent Container | Ephemeral Container (`--ephemeral`) |
| --- | --- | --- |
| **Deployment Mode** | `docker run -d --restart=always` | Managed via orchestrator or listener loop |
| **Job Lifecycle** | Remains active; processes multiple builds sequentially. | Exits immediately after processing **one** job. |
| **State Cleanliness** | Leftover workspace artifacts persist between runs. | Pure isolated state; container destroyed post-job. |
| **Container Management** | Docker auto-restart policies keep it running. | Container exits $\rightarrow$ orchestrator launches fresh container. |

## 5. Kubernetes Scaling: Actions Runner Controller (ARC)

For large-scale containerized runner infrastructure, managing raw Docker containers on plain VMs is superseded by **Actions Runner Controller (ARC)** on Kubernetes.

```text
 GitHub API Event (Workflow Queued)
               │
               ▼
┌──────────────────────────────────────────────┐
│ Actions Runner Controller (ARC Operator)     │
│ - Monitors GitHub webhook / auto-scaling queue│
└──────────────┬───────────────────────────────┘
               │ Spawns Ephemeral Pod
               ▼
┌──────────────────────────────────────────────┐
│ Kubernetes Ephemeral Runner Pod              │
│ ┌──────────────────────┐ ┌─────────────────┐ │
│ │ Runner Container     │ │ DinD Sidecar    │ │
│ └──────────────────────┘ └─────────────────┘ │
└──────────────────────────────────────────────┘

```

* **Automated Scaling:** ARC automatically scales runner Pods from `0` to `N` based on webhook events or pending job queue depth.
* **Native Ephemerality:** Pods are single-use (`RunnerCustomSet` / `AutoscalingRunnerSet`). As soon as a job finishes, Kubernetes deletes the Pod immediately and replaces it with a clean pod template.

# 4. GitHub Actions Runner Groups & Access Isolation

---

## 1. Architectural Purpose & Security Model

### What are Runner Groups?

**Runner Groups** act as organizational access control lists (ACLs) and security boundaries for compute infrastructure. They aggregate self-hosted runners (and GitHub-managed Larger Runners) into logical pools and restrict which repositories within an Organization or Enterprise are allowed to execute jobs on them.

```text
                                  ┌──────────────────────────────┐
                                  │   GitHub Organization Level  │
                                  └──────────────┬───────────────┘
                                                 │
                        ┌────────────────────────┴────────────────────────┐
                        ▼                                                 ▼
        ┌───────────────────────────────┐                 ┌───────────────────────────────┐
        │   Runner Group: "Prod-VPC"    │                 │  Runner Group: "General-CI"   │
        │   Access: [ payment-service ] │                 │   Access: [ All Repositories ]│
        └───────────────┬───────────────┘                 └───────────────┬───────────────┘
                        │                                                 │
                        ▼                                                 ▼
        ┌───────────────────────────────┐                 ┌───────────────────────────────┐
        │ Self-Hosted Runner 01 (Prod)  │                 │ Self-Hosted Runner 02 (Dev)   │
        └───────────────────────────────┘                 └───────────────────────────────┘

```

### Scope Comparison: Repo-Level vs. Org-Level Registration

| Dimension | Repository-Level Runner | Organization-Level Runner (Without Groups) | Organization-Level Runner (With Groups) |
| --- | --- | --- | --- |
| **Registration Scope** | Bound to 1 specific repository via `./config.sh --url [https://github.com/org/repo](https://github.com/org/repo)` | Registered to entire Org via `./config.sh --url [https://github.com/org](https://github.com/org)` | Registered to entire Org, then assigned to a specific Group in GitHub UI |
| **Compute Sharing** | Dedicated to single repo; idle when repo is inactive. | Shared across **all** repositories in the Organization. | Shared across **only explicitly authorized** repositories. |
| **Maintenance Burden** | High (50 repos = 50 separate runner setups). | Low (1 runner pool serves the whole Org). | Low (centralized management with fine-grained access). |
| **Security Boundaries** | Strict, isolated by default. | **Weak:** Low-security or experimental repos can run code on sensitive build servers. | **Strong:** High-security infrastructure is shielded from unauthorized repos. |

---

## 2. Core Security Use Cases

1. **Production VPC Isolation:** Restrict build servers that have direct network routes to live production environments, databases, or deployment keys so that only vetted deployment repositories can target them.
2. **Resource & Cost Safeguarding:** Prevent non-critical repositories, sandbox projects, or PR builds from consuming high-cost compute hardware (e.g., 64-core or GPU instances) reserved for core engine builds.
3. **Preventing Supply-Chain Attacks:** Protect shared runner host environments from malicious Pull Requests initiated in public or lower-tier repositories.

---

## 3. Configuration & Management Workflow

> **Requirement:** Runner Groups exist exclusively at the **Organization** and **Enterprise** levels (GitHub Team, Enterprise, or Free Organization accounts). They are not supported on personal GitHub accounts.

### Step 1: Register an Organization-Level Runner

Run `./config.sh` against the **Organization URL** rather than an individual repository URL:

```bash
./config.sh \
  --url https://github.com/Your-Organization-Name \
  --token YOUR_ORGANIZATION_REGISTRATION_TOKEN \
  --name "prod-runner-01" \
  --labels "ubuntu-latest,gpu"

```

### Step 2: Configure Access Control via GitHub UI

1. Navigate to **GitHub.com** $\rightarrow$ **Your Organization** $\rightarrow$ **Settings**.
2. In the left sidebar, navigate to **Actions** $\rightarrow$ **Runner groups**.
3. Click **New runner group**.
4. Set access visibility:
* **Selected Repositories (Recommended):** Manually check the exact repositories permitted to execute jobs on this group.
* **All Repositories:** Open access to every repository in the organization.
* **Allow Public Repositories:** Explicit toggle (disabled by default) to allow or block public repositories from sending workloads to the group.


5. Move your registered host (`prod-runner-01`) from the `Default` group into your newly created group.

---

## 4. Targeting Runner Groups in Workflow YAML

To route a workflow job to a specific runner group, define both the `group` and (optionally) specific `labels` in your pipeline's `runs-on` block:

```yaml
name: Production Deployment Pipeline

on:
  push:
    branches:
      - main

jobs:
  deploy:
    # Target runners that belong to the "Prod-VPC" group AND have matching labels
    runs-on:
      group: Prod-VPC
      labels: ubuntu-latest

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Deploy Application
        run: |
          echo "Executing deployment on Prod-VPC infrastructure..."

```

### Access Enforcement Behavior

If an unauthorized repository attempts to execute a workflow using `group: Prod-VPC`, GitHub Actions invalidates the match:

* The job is **blocked from running** on those servers.
* The workflow fails or remains queued, logging an access authorization error in the GitHub Actions UI.

## 5. Custom Docker Container Jobs

Instead of installing build dependencies directly on the host machine, GitHub Actions can run workflow steps inside an isolated Docker container on top of the runner host.

### Execution Flow

```
[ Host Runner (VM/Pod) ]
   └── Spawns ──► [ Docker Container (e.g., golang:1.22) ]
                     └── Executes ──► [ Workflow Steps ]

```

### Advanced Workflow Configuration

```yaml
name: Isolated Container Build
on:
  push:
    branches: [ main ]

jobs:
  golang-build:
    runs-on: self-hosted
    # Specifies the target container environment for job execution
    container:
      image: golang:1.22-alpine
      env:
        GOPROXY: https://proxy.golang.org,direct
      options: --user 1000
      volumes:
        - /var/run/docker.sock:/var/run/docker.sock

    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Inspect Execution Context
        run: |
          cat /etc/os-release
          go version
          whoami

```

### Why Use Container Jobs?

* **Tool Isolation:** Eliminates the need to pre-install dependencies (Node, Go, Python, Terraform) on base host images.
* **Version Parity:** Guarantees exact tool versions by using explicit Docker image tags.
* **Clean Cleanup:** Docker automatically destroys the execution container once the job finishes, leaving the underlying runner host untouched.
